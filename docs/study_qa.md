# Mini Git 학습 질문과 답변 23개

1–18번은 평가 항목 #1–#18에 각각 대응하고, 19–23번은 과제 목표 5개에 각각 대응한다. 답변은 현재 구현을 기준으로 하며, 아직 구현하지 않은 기능은 개선 방향으로 표시했다.

복잡도 표기에서 V는 커밋 수, E는 부모 간선 수, n은 정렬 항목 수다. dict와 set 연산은 평균적인 해시 조회를 가정하며, 별도 설명이 없으면 키 계산·비교 비용은 일정하다고 본다.

## 1. INIT는 무엇을 설정하며, 초기화를 다시 요청하면 어떻게 해야 하는가?

**답변:** `INIT <user_name>`은 작성자를 `user`에 저장하고, 현재 브랜치를 `main`으로 설정하며, `branches['main'] = None`으로 첫 커밋이 없는 상태를 표현한다. 초기화 전에는 저장소의 변경·조회 명령을 실행할 수 없다.

현재 구현은 두 번째 INIT를 `Repository already initialized`로 거부한다. 기존 이력을 실수로 지우지 않기 위해서다. 별도의 RESET 명령은 없으며, 빈 저장소로 다시 시작하려면 종료 후 재실행해야 한다. 명시적 재설정을 추가한다면 사용자·브랜치·커밋·그래프·인덱스·카운터를 함께 초기화해야 한다.

확인 위치: `repository.py`의 `initialize`, `require_initialized`.

## 2. BRANCH, SWITCH, COMMIT은 각각 어떤 상태를 바꾸는가?

**답변:** BRANCH는 현재 커밋 위치를 가리키는 새 브랜치를 만들고, SWITCH는 작업할 브랜치를 바꾸며, COMMIT은 새 커밋을 만들고 현재 브랜치의 위치를 이동시킨다.

| 명령 | 바뀌는 상태 | 예시 |
| --- | --- | --- |
| `BRANCH feature` | `branches`에 이름과 현재 hash 추가 | main과 feature가 같은 커밋을 가리킴 |
| `SWITCH feature` | `current_branch` 변경 | 이후 커밋은 feature에 추가됨 |
| `COMMIT second` | 새 Commit·그래프·역색인 등록, 현재 브랜치의 hash 변경 | feature만 새 커밋으로 이동함 |

BRANCH는 자동으로 전환하지 않고, SWITCH는 커밋을 생성하지 않는다. COMMIT의 부모는 현재 브랜치가 가리키던 커밋이며, 첫 커밋이면 부모가 없다.

확인 위치: `repository.py`의 `create_branch`, `switch_branch`, `commit`.

## 3. Kahn 알고리즘은 어떻게 부모를 먼저 출력하며, 옵션 정렬과는 어떤 관계인가?

**답변:** 각 커밋의 아직 출력하지 않은 부모 수를 세고, 그 수가 0인 커밋부터 큐에 넣는다. 커밋을 출력할 때마다 자식들의 남은 부모 수를 줄이고, 0이 된 자식을 큐에 추가한다. 자식은 모든 부모가 출력된 뒤에만 선택되므로 부모 우선 순서가 보장된다.

현재 기본 LOG는 이 방식을 사용한다. 반면 `LOG --sort-by=date`와 `LOG --sort-by=author`는 전체 커밋을 해당 키로 따로 정렬하므로 부모 우선을 보장하지 않는다. 두 조건을 함께 만족시키려면 현재 출력 가능한 커밋들 사이에서만 정렬 기준으로 다음 커밋을 골라야 한다.

확인 위치: `algorithms.py`의 `topological_order`, `repository.py`의 `log`.

## 4. 최단 경로가 여러 개라면 어떤 기준으로 하나를 선택하며, 왜 구분자까지 비교하는가?

**답변:** 간선 수가 같은 최단 경로 중 공백 없는 `hash1->hash2->...` 문자열의 사전순이 가장 작은 경로를 선택한다. Python 문자열 비교는 앞에서부터 문자의 유니코드 코드 포인트를 비교하고, 처음 다른 위치에서 순서를 결정한다.

목적지까지 거리가 1씩 줄어드는 후보만 남긴 뒤 `neighbor + '->'`가 가장 작은 이웃을 고른다. 이미 선택한 경로 앞부분은 같으므로 다음 부분을 비교하면 된다. hash 길이가 늘어나 한 hash가 다른 hash의 접두사가 되는 경우에도 전체 경로 문자열과 같은 기준을 쓰기 위해 구분자를 붙인다. 화면에 표시하는 ` -> `의 공백은 가독성을 위한 것이며 비교에는 쓰지 않는다.

확인 위치: `algorithms.py`의 `shortest_path`, `main.py`의 `handle_path`.

## 5. ANCESTORS는 어떻게 모든 조상을 중복 없이 찾으며, 어떤 순서로 반환하는가?

**답변:** 시작 커밋의 부모들을 스택에 넣고, 하나씩 꺼내 방문한 뒤 그 부모들도 스택에 추가하는 DFS를 사용한다. 방문한 hash를 set에 기록하여 공유 조상을 한 번만 결과에 넣고, 시작 커밋 자체는 결과에서 제외한다. 재귀 대신 스택을 사용하므로 긴 이력에서도 재귀 깊이 제한을 피한다.

예를 들어 A가 B와 C의 부모이고, D의 부모 tuple이 `(B, C)`이면 초기 스택은 `[B, C]`다. 스택의 마지막 항목부터 꺼내므로 방문 결과는 `C, A, B`가 된다. B에서 다시 만나는 A는 건너뛴다. 이 순서는 위상 정렬이나 날짜순이 아니라 DFS 방문 순서다. 현재 COMMIT 명령은 부모를 최대 하나만 만들지만, 탐색 함수는 여러 부모도 처리한다.

확인 위치: `algorithms.py`의 `find_ancestors`, `repository.py`의 `ancestors`.

## 6. 키워드 검색, 작성자 검색, LOG 정렬 옵션은 어떻게 구분하고 처리하는가?

**답변:** `SEARCH <keyword>`는 메시지 단어 역색인을 조회한다. 메시지와 검색어를 소문자로 바꾸고 공백으로 나누며, 여러 검색 단어는 모두 포함되어야 하는 AND 조건이다. 부분 문자열 검색이 아니므로 `login`과 `log`는 다르며 구두점도 자동 제거하지 않는다.

`SEARCH --author=<name>`은 `--author=`를 제거한 이름으로 작성자 역색인을 조회한다. 작성자는 전체 이름과 대소문자가 일치해야 한다. `LOG --sort-by=date`는 시각, `LOG --sort-by=author`는 작성자 문자열을 기준으로 오름차순 안정 병합 정렬한다. 지원하지 않는 정렬 값은 `Invalid args`로 거부한다.

확인 위치: `main.py`의 `handle_search`, `handle_log`, `repository.py`의 `search`, `log`.

## 7. HEAD, 브랜치, 커밋 저장소는 왜 분리하며, HEAD는 무엇을 저장하는가?

**답변:** HEAD는 현재 작업 중인 위치, 브랜치는 이름이 붙은 커밋 위치, 커밋 저장소는 실제 커밋 객체들을 관리한다. 현재 구현의 HEAD 역할은 브랜치명만 저장하는 `current_branch`가 맡는다. 현재 커밋은 `branches[current_branch]`로 찾고, 객체는 `commits[hash]`로 찾는다.

예를 들어 `current_branch = 'feature'`, `branches['feature'] = '00000002'`라면 현재 커밋은 `00000002`다. 새 커밋을 만들면 `current_branch`는 그대로이고 `branches['feature']`만 새 hash로 바뀐다. SWITCH에서는 `current_branch`가 바뀐다. 이 구조는 커밋 hash를 HEAD에도 따로 저장할 때 생기는 중복 갱신을 줄인다. 실제 Git의 detached HEAD처럼 브랜치를 거치지 않는 상태는 현재 구현하지 않았다.

확인 위치: `repository.py`의 `Repository`, `switch_branch`, `commit`.

## 8. 커밋 식별자는 어떻게 생성·저장하며, 중복과 해시 충돌은 어떻게 구분하는가?

**답변:** 1부터 증가하는 카운터를 최소 8자리 16진수 문자열로 바꾸고, dict인 `self.commits`에 `식별자 → Commit`으로 저장한다. `00000001`, `00000002`처럼 증가하며 자리수가 늘어나도 자르지 않는다. 정상 API 사용에서는 같은 세션의 식별자를 재사용하지 않는다.

식별자 중복은 같은 문자열이 다시 생성되는 문제이고, dict 내부 해시 충돌은 서로 다른 키의 해시값이 같아지는 문제다. dict는 해시 충돌 시 키의 동등성도 확인하여 서로 다른 키를 구별한다. 현재 식별자는 내용 기반 해시가 아니며, 외부에서 카운터를 되돌리는 경우를 막는 중복 검사도 없다. 카운터를 임의 변경하면 기존 커밋을 덮어쓸 수 있다.

확인 위치: `repository.py`의 `__init__`, `commit`, `get_commit`.

## 9. 역색인은 언제 갱신해야 하며, 갱신에 실패하면 어떤 문제가 생기는가?

**답변:** 새 커밋을 등록할 때 메시지 단어와 작성자에 해당 커밋 hash를 함께 추가해야 한다. 현재는 `commit`에서 `self.index.add(commit)`을 호출한다. 이때 메시지를 소문자 토큰으로 바꾸고 set으로 중복을 제거하므로 같은 메시지에 같은 단어가 여러 번 있어도 해당 단어 목록에는 한 번만 등록한다.

현재 구현에는 갱신 실패를 되돌리는 롤백이 없다. 인덱스 갱신 전에 커밋·그래프·카운터가 이미 변경되며, 도중에 실패하면 인덱스도 일부만 바뀌고 현재 브랜치는 이전 커밋에 남을 수 있다. 개선하려면 변경을 임시 상태에 준비한 뒤 함께 반영하거나, 실패 시 변경 전체를 취소하는 처리가 필요하다. 이는 현재 구현된 동작이 아니라 개선 방향이다.

확인 위치: `repository.py`의 `commit`, `index.py`의 `add`.

## 10. 공통 알고리즘을 별도 모듈로 분리하면 무엇이 좋으며, 입력·출력 계약은 무엇인가?

**답변:** CLI와 저장소 상태 관리에서 알고리즘을 분리하면 같은 함수를 여러 곳에서 재사용하고 작은 입력으로 따로 검증할 수 있다. 입력·출력 계약은 함수가 받을 자료구조와 돌려줄 결과, 오류 조건을 정한 약속이다.

| 함수 | 입력 | 출력·전제 |
| --- | --- | --- |
| `merge_sort(items, key)` | 슬라이싱 가능한 목록과 비교 키 함수 | 입력을 변경하지 않은 새 정렬 목록. 키끼리 비교 가능해야 함 |
| `topological_order(commits, children)` | hash→커밋 매핑과 부모→자식 인접 목록 | 부모 우선 hash 목록. 그래프가 일관되어야 하며 사이클이면 ValueError |
| `find_ancestors(commits, start)` | 커밋 매핑과 존재하는 시작 hash | 시작점을 제외한 조상 hash 목록. 부모 참조가 유효한 DAG 전제 |
| `shortest_path(neighbors, start, target)` | 대칭인 무방향 인접 목록과 존재하는 두 hash | 양 끝점을 포함한 경로 목록. 연결되지 않으면 빈 목록 |

예를 들어 정렬은 동률 순서, 그래프 탐색은 분기·공유 조상·연결되지 않은 노드를 작은 예시로 검증할 수 있다. 사용자에게 보여줄 오류 검증과 화면 출력은 저장소·CLI 계층에서 맡는다.

확인 위치: `algorithms.py`, `repository.py`의 알고리즘 호출부.

## 11. docstring에는 무엇을 설명해야 하며, 사용 예시는 왜 필요한가?

**답변:** 함수의 목적, 인자 의미, 반환값, 입력 전제, 오류 조건, 순서 규칙을 설명해야 한다. 코드의 처리 과정을 반복하기보다 호출하는 사람이 알아야 할 약속을 적는 것이 좋다. 짧은 예시는 설명을 실제 입력·출력과 연결한다.

현재 함수에 대응하는 사용 예시는 다음과 같다. 아래 예시는 학습 문서에 작성한 것이며 소스의 docstring을 수정한 것은 아니다.

```python
merge_sort([3, 1, 2], key=lambda value: value)
# 반환: [1, 2, 3]

shortest_path({'A': ['B'], 'B': ['A', 'C'], 'C': ['B']}, 'A', 'C')
# 반환: ['A', 'B', 'C']
```

조상 탐색은 5번의 방문 순서 예시처럼 시작점을 포함하는지, 여러 부모 중 어느 쪽을 먼저 방문하는지까지 설명하면 결과를 예측하기 쉽다.

확인 위치: `algorithms.py`의 모듈·함수 docstring.

## 12. 사이클 검출과 커밋 불변성은 각각 왜 필요하며, 어떻게 구현했는가?

**답변:** 사이클 검출은 잘못 구성된 그래프를 발견하고, 커밋 불변성은 이미 만든 이력이 나중에 바뀌는 것을 막는다. Kahn 알고리즘을 마친 뒤 출력 노드 수가 전체 커밋 수보다 적으면 순환 관계 때문에 처리하지 못한 노드가 있는 것이므로 `ValueError('Cycle detected')`를 발생시킨다.

`Commit`은 `@dataclass(frozen=True)`로 선언하고 부모를 tuple로 저장하여 일반적인 필드 재대입과 부모 항목 변경을 막는다. 새 커밋은 기존 커밋만 부모로 참조하므로 정상 생성 과정에서는 사이클이 생기지 않는다. 다만 저장소의 dict와 인접 목록까지 불변인 것은 아니며, 위상 정렬의 사이클 검출도 부모 정보와 자식 목록이 서로 일치한다는 전제를 갖는다.

확인 위치: `repository.py`의 `Commit`, `algorithms.py`의 `topological_order`.

## 13. 기본 LOG가 보장하는 출력 순서는 정확히 무엇인가?

**답변:** 현재 브랜치의 이력만이 아니라 전체 저장소의 커밋을 대상으로, 모든 부모가 자식보다 먼저 나오는 위상 순서를 보장한다. 기본 LOG는 `topological_order`가 반환한 hash 순서대로 커밋 객체를 조회하여 출력한다.

예를 들어 A에서 B와 C로 갈라졌다면 A는 B와 C보다 먼저 나와야 하지만 B와 C 사이의 순서는 부모 우선 조건만으로 결정되지 않는다. 현재 구현은 준비 큐에 들어온 순서를 따른다. 따라서 기본 LOG를 전체 생성 순서, 날짜순, 또는 유일한 정답 순서라고 설명하면 안 된다.

확인 위치: `repository.py`의 `log`, `algorithms.py`의 `topological_order`.

## 14. PATH는 왜 무방향 그래프에서 BFS를 사용하며, 예외 상황은 어떻게 처리하는가?

**답변:** 이 과제의 PATH는 부모로 올라가는 이동과 자식으로 내려가는 이동을 모두 허용하므로 각 부모·자식 연결을 양방향 이웃으로 등록한다. 모든 간선의 이동 비용이 같아 BFS로 최소 간선 수의 경로를 찾을 수 있다. 일반적인 DFS는 먼저 찾은 경로가 최단이라는 보장이 없다.

현재 구현은 목적지에서 BFS로 거리를 구하고, 출발지부터 거리를 1씩 줄여 경로를 복원한다. 두 커밋이 존재하지만 연결되지 않았으면 빈 목록을 반환하고 CLI가 `No path`를 출력한다. 같은 커밋을 양 끝점으로 지정하면 hash 하나를 반환한다. 없는 hash는 탐색 전에 `Unknown commit` 오류로 구분한다.

확인 위치: `repository.py`의 `path`, `algorithms.py`의 `shortest_path`.

## 15. 직접 구현한 병합 정렬은 왜 안정적이며, 시간·공간 복잡도는 얼마인가?

**답변:** 목록을 반으로 나눠 각각 정렬한 뒤 작은 항목부터 합친다. 두 키가 같으면 `<=` 조건으로 왼쪽 목록의 항목을 먼저 선택하므로, 같은 키를 가진 항목의 원래 상대 순서가 유지되는 안정 정렬이다. `sorted()`나 `list.sort()`를 사용하지 않는다.

각 분할 단계의 전체 병합 작업은 O(n)이고 단계 수가 O(log n)이므로 최선·평균·최악 시간복잡도는 모두 O(n log n)이다. 현재 구현처럼 부분 목록과 병합 결과를 만드는 방식의 최대 추가 공간은 O(n)이고, 재귀 호출 깊이는 O(log n)이다. 이 분석은 키 계산·비교 비용을 일정하게 본다.

확인 위치: `algorithms.py`의 `merge_sort`.

## 16. 역색인의 어떤 연산이 평균 O(1)이며, 전체 검색은 얼마나 걸리는가?

**답변:** dict에서 검색 단어 또는 작성자에 대응하는 후보 목록을 찾는 키 조회가 평균 O(1)이다. 결과 목록을 복사하거나 후보를 비교하는 작업까지 O(1)인 것은 아니다. 문자열 해싱 비용도 별도로 고려해야 한다.

현재 여러 단어 검색은 각 후보 목록을 set으로 바꾸고 가장 짧은 목록의 hash가 모든 set에 들어 있는지 검사한다. 고유 검색 단어 수가 k, 후보 목록 길이가 각각 Lᵢ, 최단 목록 길이가 m이면 토큰화 이후 평균 시간은 O(k + ΣLᵢ + k·m)이다. 한 단어의 후보가 r개이면 결과 생성까지 O(r + 1)이고, 작성자 검색도 결과 복사 때문에 O(r + 1)이다. 검색된 hash에 해당하는 커밋만 가져오므로 전체 커밋을 다시 훑지 않는다.

확인 위치: `index.py`의 `search_keyword`, `search_author`, `repository.py`의 `search`.

## 17. 커밋과 검색 데이터가 많아지면 어디가 병목이며, 어떻게 개선할 수 있는가?

**답변:** 기본 LOG와 PATH는 O(V + E), 옵션 LOG는 O(V log V)의 작업이 필요하다. 모든 커밋·그래프·역색인을 메모리에 보관하므로 데이터가 커질수록 메모리도 늘어난다. 특히 흔한 단어는 후보 목록이 길고, 검색할 때마다 그 목록을 set으로 복사하는 비용도 커진다.

개선 방향으로는 정렬된 후보 목록의 교집합, 비트맵, 반복 조회 캐시, 영속 저장소, 결과 페이지 처리를 검토할 수 있다. 인덱스를 단어·작성자 키별로 분산하면 저장과 조회 부담을 나눌 수 있지만, 여러 키의 결과를 합치는 비용과 커밋·인덱스의 일관성도 관리해야 한다. 현재 프로그램에는 이러한 개선이나 분산 처리가 구현되어 있지 않다.

확인 위치: `repository.py`의 상태 저장 구조, `index.py`의 후보 목록 처리, README의 항목 #17.

## 18. 카운터 식별자와 난수 식별자는 재현성과 테스트에 어떤 차이를 만드는가?

**답변:** 카운터는 새 저장소에서 동일한 명령 순서를 실행하면 같은 식별자를 만들므로 예상 hash와 부모·브랜치 상태를 고정된 값으로 검사하기 쉽다. 하지만 세션마다 1부터 시작하므로 여러 저장소를 합칠 때의 전역 유일성은 보장하지 않는다.

난수 식별자는 충분한 식별자 공간을 사용하면 독립적으로 생성하기 편하지만, 충돌 가능성을 고려한 검사·재시도가 필요하다. 테스트에서는 생성기를 주입해 결과를 통제하거나 실제 반환된 식별자로 관계를 검증해야 한다. 현재 구현은 카운터를 사용하며, timestamp는 실행 시각이므로 카운터가 같아도 전체 출력이 같지는 않다.

확인 위치: `repository.py`의 `next_commit_id`, `commit`.

## 19. [과제 목표 1] 커밋 그래프는 어떻게 표현하며, Git의 커밋 구조는 왜 DAG인가?

**답변:** 커밋을 정점으로, 커밋과 부모의 참조 관계를 방향 간선으로 표현한다. 각 커밋은 자신의 식별자·메시지·작성자·시각·부모 식별자들을 갖는다. 현재 구현은 커밋 객체를 `commits`에, 자식 탐색용 목록을 `children`에 저장하고, PATH를 위한 양방향 목록을 `neighbors`에 따로 둔다. 실제 파일 스냅샷은 추적하지 않는다.

DAG는 방향이 있고 순환이 없는 그래프다. 새 커밋은 이미 존재하는 부모를 참조하고 기존 커밋의 부모 관계를 바꾸지 않으므로, 부모 참조를 계속 따라가 새 커밋 자신에게 돌아오는 순환이 생기지 않는다. 이 성질은 시계의 timestamp가 정확한지와는 무관하다. 분기는 한 부모에서 여러 자식이 생기는 것이고, 병합은 한 커밋이 여러 부모를 갖는 것이므로 둘 다 순환 없이 표현할 수 있다.

부모 참조의 방향은 `자식 → 부모`이고, 부모 우선 출력을 설명할 때 쓰는 의존 관계는 `부모 → 자식`이다. 두 표현은 방향을 뒤집은 관계이며 모두 DAG다. 현재 모델은 여러 부모를 담을 수 있지만 CLI의 MERGE는 구현하지 않았다.

## 20. [과제 목표 2] 부모가 먼저 출력되는 로그를 만들려면 왜 위상 정렬이 필요한가?

**답변:** 요구사항이 날짜나 이름의 대소가 아니라 “각 부모가 모든 자식보다 앞서야 한다”라는 선행 관계이기 때문이다. 날짜순은 시계 문제를, 작성자순은 부모·자식 관계를 반영하지 못하므로 이 조건을 일반적으로 보장하지 않는다. 이런 부분적인 순서 제약을 만족하는 전체 나열이 위상 순서다.

Kahn 알고리즘에서는 남은 부모가 없는 루트부터 출력하고, 출력한 커밋의 자식들에서 부모 수를 하나씩 줄인다. 모든 부모가 처리된 자식만 다음 후보가 된다. 커밋과 간선을 각각 한 번씩 처리하므로 O(V + E)다. 출력 가능한 후보가 여러 개면 그 안에서 날짜나 작성자를 기준으로 선택할 수 있지만, 현재 옵션 LOG는 이런 결합 방식이 아니라 별도의 전체 정렬이다.

## 21. [과제 목표 3] 두 커밋의 최단 경로와 한 커밋의 모든 조상은 어떻게 다르게 탐색하는가?

**답변:** 최단 경로는 무방향 이웃을 따라 BFS로 찾고, 모든 조상은 부모 방향만 따라 DFS로 모은다. PATH는 출발지·목적지 사이의 한 경로를 반환하고, ANCESTORS는 시작점 이전의 모든 조상을 중복 없이 반환한다.

예를 들어 A의 자식이 B와 C라면 B에서 C로 가는 PATH는 `B → A → C`다. 반면 B의 조상은 A이며 형제인 C는 포함되지 않는다. 그래프가 클 때 탐색 시간은 최악 O(V + E)이고, 조상 탐색은 실제 도달 가능한 조상 부분만 살펴본다. BFS의 거리 표와 DFS의 방문 집합은 중복 처리를 막는다.

현재 PATH는 목적지에서 거리 표를 만든 뒤 최단 경로를 복원하고, 동률이면 경로 문자열 사전순을 적용한다. ANCESTORS는 스택에 마지막으로 넣은 부모부터 방문하므로 반환 순서가 최단 거리순이나 부모 우선 순서는 아니다.

## 22. [과제 목표 4] 정렬 알고리즘의 구현 원리, 평균·최악 시간복잡도, 안정성을 어떻게 설명할 수 있는가?

**답변:** 이 과제의 병합 정렬은 “분할 → 각 부분 재귀 정렬 → 두 정렬 목록 병합”으로 설명할 수 있다. 크기 n인 입력을 두 부분으로 나누는 깊이는 log n 수준이고, 각 깊이에서 전체 n개 항목을 병합하므로 평균과 최악 모두 O(n log n)이다. 현재 구현은 이미 정렬된 입력도 계속 분할·병합하므로 최선도 O(n log n)이다.

안정성은 키가 같은 항목들의 입력 순서가 출력에서도 유지되는 성질이다. 예를 들어 작성자가 모두 Alice인 커밋 X와 Y가 입력에 X, Y 순서로 있다면 작성자 기준 정렬 후에도 X, Y여야 한다. 병합에서 키가 같을 때 왼쪽 항목을 먼저 꺼내므로 이 성질이 유지된다. 추가 공간은 O(n), 재귀 깊이는 O(log n)이며, 시간 분석은 키 계산·비교 비용을 일정하게 본다는 전제를 갖는다.

## 23. [과제 목표 5] 역색인은 어떻게 동작하며, 순회 검색보다 빠른 이유를 복잡도로 설명할 수 있는가?

**답변:** 순회 검색은 “각 커밋에 어떤 단어가 있는가”를 검색할 때마다 확인한다. 역색인은 미리 “이 단어가 들어 있는 커밋은 무엇인가”를 저장한다. 예를 들어 `login → [00000002, 00000005]`가 있으면 다른 커밋의 메시지를 읽지 않고 두 후보만 조회한다. 작성자도 같은 방식으로 이름에서 커밋 목록을 찾는다.

전체 메시지 길이의 합을 M이라 하면 메시지를 전부 읽는 순회 검색은 한 번에 O(M)이 든다. 역색인의 단일 단어 검색은 토큰화·문자열 해싱 비용을 별도로 보면 키 조회 평균 O(1), 결과 r개 처리 O(r)로 총 O(r + 1)이다. 여러 단어는 후보 교집합 비용이 추가되며 현재 구현의 자세한 식은 16번과 같다.

대신 커밋 생성 시 토큰화·인덱스 갱신 비용과 후보 목록을 저장할 공간을 미리 부담한다. 모든 커밋에 등장하는 흔한 단어라면 r이 V에 가까워 검색도 O(V)에 가까워지므로 항상 상수 시간이라고 할 수 없다. 역색인은 검색 대상이 전체 데이터보다 작은 후보 집합으로 줄어들 때 특히 효과적이다.
