# B3-2 기초·핵심 지식

## 이 미션에서 배우는 것

커밋의 이력과 브랜치의 위치를 메모리에 관리하는 Mini Git을 만듭니다.<br>
기록 사이의 관계를 그래프로 표현하고, 목적에 맞는 탐색과 정렬을 선택하는 법을 배웁니다.<br>
브랜치와 HEAD가 가리키는 위치, 부모 우선 로그와 최단 경로의 차이를 설명할 수 있어야 합니다.<br>
역색인이 검색 대상을 줄이는 원리와 직접 구현한 병합 정렬의 선택 이유도 익힙니다.

## 1. 먼저 알아야 할 기초

### 기록할 정보와 기록 사이의 관계

이 미션에서는 기록 하나에 식별자, 메시지, 작성자, 시각, 부모 식별자를 담습니다. 메시지는 무엇을 했는지 설명하고, 부모 식별자는 어떤 기록에서 이어졌는지 나타냅니다. 메시지만 저장하면 작업 내용은 알 수 있어도 이력이 갈라진 지점을 찾기는 어렵습니다.

하나의 기록에서 로그인 작업과 결제 작업을 따로 시작했다면 두 작업의 부모는 같습니다. 두 기록의 작성 시각이 다르더라도 서로 부모와 자식인 것은 아닙니다. **시각은 언제 만들었는지를, 부모 관계는 어디에서 이어졌는지를 알려 줍니다.**

### 질문에 따라 관계를 읽는 방법이 달라진다

- `LOG`: 모든 기록을 부모가 먼저 나오도록 나열하려면 어떤 순서여야 할까?
- `PATH`: 두 기록 사이에서 연결을 가장 적게 거치는 길은 무엇일까?
- `ANCESTORS`: 부모 방향으로 계속 거슬러 올라가면 어떤 기록을 만날까?
- `SEARCH`: 특정 단어나 작성자에 해당하는 기록은 무엇일까?

PATH에서는 부모와 자식 양쪽으로 이동하지만, ANCESTORS에서는 부모 쪽으로만 이동합니다. LOG의 부모 우선 순서와 날짜순 정렬도 구분해야 합니다. 같은 기록을 조회하더라도 질문에 맞는 처리 방법을 골라야 합니다.

### 현재 프로그램의 학습 범위

현재 Mini Git은 커밋 정보와 관계를 다루는 학습용 프로그램입니다. 실제 파일 내용을 저장하거나 복원하지 않으며, 종료하면 메모리의 기록이 사라집니다. 실제 Git의 파일 저장 방식과 저장소 호환성을 구현한 것으로 이해하면 안 됩니다.

이 미션에서는 `list`, `dict`, `set`을 사용할 수 있지만 `sorted()`·`list.sort()` 같은 표준 정렬 API와 그래프 전용 라이브러리로 핵심 알고리즘을 대신하지 않습니다. 현재 코드는 탐색·정렬·역색인을 나누어 구현합니다.

## 2. 미션에서 사용하는 용어

### 2-1. CLI와 REPL: 명령을 받아 실행하는 방식

**기본 설명**

CLI(Command Line Interface)는 텍스트 명령으로 프로그램을 조작하는 인터페이스입니다. REPL(Read–Eval–Print Loop)은 입력을 읽고, 해석해 실행하고, 결과를 보여 주는 과정을 반복하는 방식입니다.

**비유 설명**

안내 창구에서 요청을 말하고 답을 받은 뒤 다음 요청을 하는 상황과 비슷합니다. CLI는 요청을 전달하는 방식이고, REPL은 창구가 다음 요청을 계속 기다리는 운영 방식입니다.

**작은 예시와 미션에서의 역할**

`COMMIT "Add login"`을 입력하면 기록을 만들고 다음 명령을 기다립니다. 공백을 포함한 메시지를 인자 하나로 읽기 위해 `shlex.split()`을 사용합니다. 명령어는 대소문자를 구분하지 않지만 브랜치명과 작성자명까지 소문자로 바꾸지는 않습니다.

### 2-2. 커밋과 저장소: 기록 하나와 기록을 관리하는 공간

**기본 설명**

커밋(commit)은 작업 메시지와 작성자·시각·부모 정보를 가진 기록입니다. 저장소(repository)는 커밋들과 브랜치, 그 관계를 관리하는 공간입니다. 이 구현의 커밋에는 파일 내용의 스냅샷이 포함되지 않습니다.

**비유 설명**

커밋은 이전 기록의 번호가 적힌 작업 일지 한 장, 저장소는 일지와 분류표를 보관하는 기록실과 비슷합니다. 다만 이 프로그램의 일지에는 실제 파일 사본이 들어 있지 않습니다.

**작은 예시와 미션에서의 역할**

첫 커밋에는 부모가 없고 다음 커밋은 현재 작업 위치의 커밋을 부모로 기록합니다. 이 연결이 로그·경로·조상 조회의 바탕입니다.

### 2-3. hash와 해시 맵: 식별자와 조회 구조의 차이

**기본 설명**

여기서 `hash`는 커밋 식별자 필드의 이름입니다. 현재 구현은 증가 정수를 최소 8자리의 16진수 문자열로 바꿉니다. `00000009` 다음은 `0000000a`입니다. 내용을 계산한 암호학적 해시는 아닙니다.

해시 맵(hash map)은 키에 대응하는 값을 빠르게 찾기 위한 자료구조입니다. 이 프로그램은 Python의 `dict`로 `커밋 hash → 커밋 정보`를 관리합니다. 식별자를 만드는 방법과 그 식별자로 조회하는 구조는 별개입니다.

**비유 설명**

커밋 hash는 일지의 관리 번호이고, 해시 맵은 관리 번호로 일지를 찾는 조회 대장입니다. 번호 발급과 대장에서의 조회는 서로 다른 작업입니다.

**미션에서의 역할**

전체 hash로 커밋을 직접 찾습니다. 카운터를 재사용하지 않는 정상 동작에서는 세션 내 식별자가 겹치지 않으며, 8자리를 넘어도 잘라내지 않습니다. 새 세션에서는 다시 1부터 시작하므로 세션 간 유일성은 보장하지 않습니다. Python dict 내부의 해시 충돌은 서로 다른 식별자를 같은 커밋으로 취급한다는 뜻이 아닙니다.

### 2-4. 브랜치와 HEAD: 기록을 가리키는 위치

**기본 설명**

브랜치(branch)는 특정 커밋을 가리키는 이름입니다. HEAD는 현재 작업 위치입니다. 이 구현에서는 현재 브랜치를 확인한 뒤 그 브랜치가 가리키는 커밋을 찾습니다. 첫 커밋 전에는 브랜치 이름만 있고 가리키는 커밋은 없습니다.

**비유 설명**

브랜치는 이름표가 있는 책갈피이고, HEAD는 지금 사용하는 책갈피를 고르는 표시입니다. 책갈피를 하나 더 만든다고 일지를 복사하는 것은 아닙니다.

**작은 예시와 미션에서의 역할**

main과 feature가 같은 커밋을 가리킬 수 있습니다. `SWITCH feature` 이후 COMMIT을 실행하면 feature만 새 커밋으로 이동합니다.

### 2-5. 그래프·노드·간선·인접 목록: 관계를 저장하는 표현

**기본 설명**

그래프(graph)는 대상과 그 사이의 연결을 표현합니다. 대상 하나가 노드(node), 연결 하나가 간선(edge)입니다. 여기서는 커밋이 노드이고 부모 관계가 간선입니다. 간선에 이동 방향이 있으면 방향 그래프이고, 양쪽 이동을 허용하면 무방향 그래프입니다.

인접 목록(adjacency list)은 각 노드에 바로 연결된 노드들을 모아 두는 표현입니다. 필요한 이웃만 바로 확인할 수 있습니다.

**비유 설명**

역을 노드, 역 사이 구간을 간선으로 보는 노선도와 비슷합니다. 각 역에서 바로 갈 수 있는 역들을 적은 표가 인접 목록입니다. 방향은 실제 이동을 허용하는 쪽에 대응합니다.

**작은 예시와 미션에서의 역할**

A에서 이어진 커밋이 B, C라면 자식 목록은 `A: [B, C]`, 부모 목록은 `B: [A]`, `C: [A]`입니다. PATH에서는 부모와 자식을 모두 이웃으로 관리합니다. 목적별 목록을 유지하면 이웃을 찾으려고 매번 전체 커밋을 읽을 필요가 없습니다.

### 2-6. 부모·자식·조상과 DAG: 되돌아오지 않는 이력

**기본 설명**

부모(parent)는 새 커밋의 바탕이 된 기존 커밋이고 자식(child)은 그 부모에서 이어진 새 커밋입니다. 조상(ancestor)은 부모와 부모의 부모를 계속 따라가며 만나는 커밋입니다. 자기 자신은 조상 결과에서 제외합니다.

DAG(Directed Acyclic Graph, 방향성 비순환 그래프)는 방향을 따라 출발점으로 돌아오는 순환이 없는 그래프입니다. `C → B → A`에서 다시 `A → C`를 연결하면 순환이 생겨 DAG가 아닙니다.

**비유 설명**

선행 작업을 적은 작업표와 비슷합니다. C가 B 다음이고 B가 A 다음이라면, A가 다시 C 다음이라고 정할 수는 없습니다. 그러면 어떤 작업도 먼저 시작할 수 없습니다.

**미션에서의 역할**

커밋 이력을 순환 없이 유지해야 부모 관계를 모순 없이 읽을 수 있습니다. 현재 COMMIT은 부모가 최대 하나라 트리 또는 여러 트리의 모음을 만듭니다. 이는 DAG의 한 종류입니다. 복수 부모를 담는 모델과 탐색은 있지만 MERGE 명령은 구현하지 않았습니다.

### 2-7. 탐색·큐·스택: 다음 처리 대상을 정하기

**기본 설명**

탐색(traversal)은 연결을 따라 필요한 노드를 방문하는 과정입니다. 큐(queue)는 먼저 넣은 항목을 먼저 꺼내는 FIFO(First In, First Out), 스택(stack)은 나중에 넣은 항목을 먼저 꺼내는 LIFO(Last In, First Out) 방식입니다. 방문 표시를 남기면 같은 노드를 여러 경로로 만나도 중복 처리를 줄일 수 있습니다.

**비유 설명**

큐는 먼저 줄 선 사람부터 처리하는 대기 줄이고, 스택은 맨 위에 놓은 접시부터 꺼내는 접시 더미와 비슷합니다. 대기 대상을 꺼내는 쪽이 다릅니다.

**작은 예시와 미션에서의 역할**

A, B, C를 차례로 넣으면 큐에서는 A가, 스택에서는 C가 먼저 나옵니다. 현재 BFS와 칸 알고리즘은 `collections.deque`를 큐로, DFS는 목록의 끝을 스택으로 사용합니다. deque는 양 끝 삽입·제거가 빠르므로 큐 앞에서 꺼내기에 적합합니다. [Python 공식 설명](https://docs.python.org/3/library/collections.html#collections.deque)

### 2-8. BFS: 가까운 노드부터 방문하는 너비 우선 탐색

**기본 설명**

BFS(Breadth-First Search)는 시작점에서 간선을 적게 거치는 노드부터 방문합니다. 큐에서 노드를 꺼내고 아직 발견하지 않은 이웃의 거리를 현재 거리보다 1 크게 기록해 큐 뒤에 넣습니다. 처음 발견할 때 방문 표시를 해 같은 노드의 중복 등록을 막습니다.

모든 간선을 같은 비용으로 보면 거리 0인 노드 다음에 거리 1인 노드들, 그다음 거리 2인 노드들이 처리됩니다. 따라서 처음 기록한 거리가 최소 간선 수입니다. 간선마다 비용이 다른 경우의 최소 비용 경로까지 보장하지는 않습니다.

**비유 설명**

출발역에서 구간 한 개로 갈 수 있는 역을 먼저 확인하고, 그다음 두 개로 갈 수 있는 역을 확인하는 방식입니다. 여기서 거리는 소요 시간이 아니라 거치는 구간 수입니다.

**작은 예시**

양방향 연결이 `A—B`, `A—C`, `B—D`이고 A의 이웃을 B, C 순서로 확인한다고 합시다.

| 꺼낸 노드 | 새로 기록한 거리 | 처리 후 큐: 왼쪽이 다음 대상 |
| --- | --- | --- |
| 시작 전 | A=0 | A |
| A | B=1, C=1 | B, C |
| B | D=2 | C, D |
| C | 없음 | D |
| D | 없음 | 비어 있음 |

**미션에서의 역할**

현재 PATH에서 실제로 사용합니다. 목적지에서 BFS로 거리를 구한 뒤 출발지에서 경로를 복원합니다. 거리를 구하는 것과 여러 최단 경로 중 하나를 선택하는 규칙은 구분해야 합니다.

### 2-9. DFS: 한쪽을 깊게 따라가는 깊이 우선 탐색

**기본 설명**

DFS(Depth-First Search)는 한쪽 경로를 깊게 따라간 뒤 더 진행할 곳이 없으면 남은 경로로 돌아옵니다. 재귀나 스택으로 구현할 수 있습니다. 현재 구현은 스택에서 꺼낸 노드를 이미 방문했다면 건너뜁니다.

**비유 설명**

갈림길에서 한쪽 복도를 끝까지 확인한 뒤 돌아와 다른 복도를 살피는 방식입니다. 먼저 찾은 길이 가장 짧다는 보장은 없습니다.

**작은 예시**

복수 부모를 지원하는 알고리즘의 설명용 입력이며 현재 필수 CLI의 재현 예는 아닙니다. M의 부모 목록이 `[A, B]`이고 A와 B의 부모가 모두 R이라고 합시다.

스택 오른쪽에서 꺼내면 `[A, B]` → B 방문 → `[A, R]` → R 방문 → `[A]` → A 방문 → R은 이미 방문했으므로 건너뜁니다. 결과는 `B, R, A`이며 시작 M과 중복 R은 추가하지 않습니다.

**미션에서의 역할**

현재 ANCESTORS에서 실제로 사용합니다. 모든 조상을 찾는 목적에는 최단 거리 순서가 필요하지 않습니다. 스택을 사용해 긴 이력에서도 재귀 깊이에 의존하지 않습니다. 방문 순서는 부모를 스택에 넣는 순서에 따라 달라집니다.

### 2-10. 위상 정렬과 칸 알고리즘: 선행 관계를 지키는 순서

**기본 설명**

위상 정렬(topological sort)은 방향 그래프의 모든 선행 관계를 지키도록 노드를 나열하는 것입니다. 이 미션에서는 모든 부모가 자식보다 앞에 나와야 합니다. 가능한 순서는 여러 개일 수 있고, 순환이 있으면 전체를 위상 정렬할 수 없습니다.

칸(Kahn) 알고리즘은 위상 정렬을 구하는 한 방법입니다. 진입 차수(in-degree)는 노드로 들어오는 간선 수입니다. 부모→자식 방향으로 표현하면 아직 처리하지 않은 부모 수에 해당합니다.

1. 각 노드의 진입 차수를 계산하고 0인 노드를 큐에 넣습니다.
2. 하나를 꺼내 결과에 추가하고 그 노드에서 자식으로 나가는 간선을 처리한 것으로 봅니다.
3. 각 자식의 남은 진입 차수를 1씩 줄이고 0이 된 자식을 큐에 넣습니다.
4. 큐가 빌 때까지 반복합니다. 전체 노드를 처리하지 못했다면 순환을 확인해야 합니다.

**비유 설명**

선수 과목을 모두 마친 과목만 다음 수강 대상으로 고르는 방식입니다. 과목 하나를 끝낼 때마다 후속 과목의 남은 조건 수를 줄입니다. 수업이 열린 시각보다 선행 조건 충족 여부가 중요합니다.

**작은 예시**

부모→자식 연결이 `A→B`, `A→C`, `B→D`라면 초기 진입 차수는 A=0, B=1, C=1, D=1입니다. A의 자식 목록 순서는 B, C라고 합시다.

| 출력한 노드 | 자식의 남은 부모 수 변화 | 처리 후 큐 |
| --- | --- | --- |
| 시작 전 | 초기값 유지 | A |
| A | B: 1→0, C: 1→0 | B, C |
| B | D: 1→0 | C, D |
| C | 변화 없음 | D |
| D | 변화 없음 | 비어 있음 |

출력은 `A, B, C, D`입니다. `A, B, D, C`도 부모 우선 조건 자체는 만족하지만 위 큐 처리에서는 첫 번째 순서가 나옵니다.

**미션에서의 역할**

현재 기본 LOG에서 실제로 사용합니다. 저장된 `parents`는 자식→부모 방향이지만 알고리즘은 `children`의 부모→자식 연결과 남은 부모 수를 사용합니다. 이 방향을 기준으로 진입 차수를 해석해야 합니다. 원본 간선을 삭제하는 대신 보조 카운터를 줄입니다.

| 방법 | 해결하는 질문 | 현재 사용 기능 |
| --- | --- | --- |
| BFS | 최소 몇 개의 간선을 거쳐 갈 수 있는가? | PATH의 거리 계산 |
| DFS | 부모를 계속 따라가면 어떤 노드들을 만나는가? | ANCESTORS |
| 위상 정렬: 칸 알고리즘 | 모든 부모를 먼저 놓는 전체 순서는 무엇인가? | 기본 LOG |

칸 알고리즘도 큐를 쓰지만 BFS의 최단 거리 계산과는 처리 조건이 다릅니다. DFS 기반 위상 정렬도 가능하지만 현재 LOG는 칸 알고리즘을 사용합니다.

### 2-11. 역색인·토큰·교집합: 검색 대상을 줄이는 방법

**기본 설명**

역색인(inverted index)은 문서에서 단어를 읽는 방향을 뒤집어 단어로 해당 문서들을 찾는 구조입니다. 여기서는 `단어 → 커밋 hash 목록`과 `작성자 → 커밋 hash 목록`을 관리합니다.

토큰(token)은 검색을 위해 나눈 단위입니다. 현재 메시지는 소문자로 바꾼 뒤 공백으로 나누므로 `Add LOGIN`은 add, login 두 토큰이 됩니다. 여러 단어 검색은 모든 후보 목록에 공통으로 있는 커밋만 남기는 교집합, 즉 AND 조건을 적용합니다.

**비유 설명**

책 뒤의 찾아보기에서 단어를 보고 관련 쪽 번호로 바로 가는 방식과 비슷합니다. 여러 단어를 모두 설명하는 쪽을 찾으려면 각 목록에서 겹치는 번호를 골라야 합니다.

**작은 예시와 미션에서의 역할**

add의 목록이 `[c1, c2]`, login의 목록이 `[c2, c3]`이면 `SEARCH "add login"`의 후보는 c2입니다. SEARCH는 이 후보만 저장소에서 조회합니다. 작성자 검색은 단어로 나누지 않고 전체 이름을 대소문자까지 일치시킵니다.

### 2-12. 직접 정렬·병합 정렬·안정성: 비교 기준에 맞춰 순서 만들기

**기본 설명**

정렬은 비교 기준에 따라 항목을 재배치하는 작업입니다. 직접 정렬한다는 것은 비교와 이동 과정을 구현한다는 뜻이며, 내장 함수로 목록을 만드는 것까지 금지한다는 뜻은 아닙니다.

병합 정렬(merge sort)은 목록을 반으로 나누어 각각 정렬한 뒤 두 부분의 앞 항목을 비교해 합칩니다. 안정 정렬(stable sort)은 기준이 같은 항목끼리 원래 상대 순서를 유지합니다.

**비유 설명**

이름순으로 정리된 두 서류 묶음의 앞 이름을 비교하며 하나로 합치는 과정과 비슷합니다. 같은 이름이면 원래 앞쪽 묶음의 서류를 먼저 골라 동률 항목의 순서를 보존합니다.

**작은 예시와 미션에서의 역할**

작성자 기준으로 왼쪽이 `[Alice(c1), Kim(c2)]`, 오른쪽이 `[Alice(c3)]`이면 결과는 `[Alice(c1), Alice(c3), Kim(c2)]`입니다. 같은 Alice인 c1과 c3의 원래 순서를 유지합니다. 현재 옵션 LOG가 직접 구현한 안정 병합 정렬을 사용합니다.

## 3. 이번 미션의 핵심

### 3-1. 브랜치를 만들면 커밋을 복사할까?

다음 상태를 생각해 보세요.

| 작업 | main | feature | 현재 브랜치 |
| --- | --- | --- | --- |
| INIT Alice | None | 없음 | main |
| COMMIT root | 00000001 | 없음 | main |
| BRANCH feature | 00000001 | 00000001 | main |
| SWITCH feature | 00000001 | 00000001 | feature |
| COMMIT login | 00000001 | 00000002 | feature |

새 브랜치는 현재 hash를 새 이름에 연결합니다. 이후 커밋을 만들면 현재 브랜치의 참조만 새 hash로 바뀝니다. 과거 이력을 복사하지 않고 공유하면서 브랜치별로 작업을 이어가는 구조입니다.

### 3-2. 왜 DAG인가?

커밋 생성은 **현재 HEAD가 가리키는 기존 커밋을 부모**로 삼는 새 노드만 추가합니다. 기존 커밋의 부모는 수정하지 않습니다. 부모를 계속 따라가면 생성 시점이 더 이른 노드만 만나므로 자기 자신으로 돌아올 수 없습니다.

부모 튜플과 `@dataclass(frozen=True)`는 일반적인 부모 변경·필드 재대입을 제한해 이 규칙을 유지하도록 돕습니다. 다만 저장소의 dict와 그래프 목록까지 불변으로 만드는 것은 아닙니다. frozen만으로 임의 그래프의 DAG가 자동 보장되는 것도 아니며, 새 노드만 추가하는 생성 규칙과 그래프 자료의 일관성이 함께 필요합니다.

### 3-3. LOG와 위상 정렬

최신순으로만 출력하면 자식이 부모보다 먼저 나올 수 있습니다. 기본 LOG는 칸 알고리즘으로 아직 출력하지 않은 부모가 없는 커밋만 선택합니다. 여러 브랜치의 커밋을 전체 저장소에서 조회하면서도 선행 관계를 지키기 위한 선택입니다.

서로 조상·자손이 아닌 커밋끼리는 큐에 들어온 순서를 따르며 전체 생성 순서와 항상 같지는 않습니다. 일관된 그래프에서 처리한 노드 수가 전체보다 적으면 `Cycle detected` 오류를 냅니다.

`LOG --sort-by=date`와 `LOG --sort-by=author`는 사용자가 다른 정렬 기준을 요청한 별도 모드입니다. 각각 시각과 작성자 이름의 오름차순이며, 기본 LOG의 부모 우선 규칙을 추가로 강제하지 않습니다.

### 3-4. PATH는 BFS로 거리를 구한다

갈라진 두 브랜치 사이의 길을 찾으려면 부모로 올라갔다가 다른 자식으로 내려올 수 있어야 합니다. 그래서 PATH는 부모 간선을 **양방향**으로 취급하고 부모와 자식을 함께 이웃으로 저장합니다.

예를 들어 `feature 커밋 → root → main 커밋`은 부모로 갔다가 다른 자식으로 내려오는 2간선 경로입니다. 부모 방향만 탐색하면 이 경로를 놓칩니다.

먼저 목적지에서 BFS로 각 노드의 목적지까지 거리를 기록합니다. 그런 다음 출발지에서 **거리가 정확히 1 줄어드는 이웃만** 선택합니다. 이 조건으로 최단 경로를 유지하고 복원 중 순환에 빠지지 않습니다. 선택할 이웃이 여러 개면 `hash + "->"`가 가장 작은 것을 고릅니다.

#### 최단 거리 동률 예

알고리즘 함수의 입력으로 다음 연결을 생각합니다. 필수 COMMIT만으로는 다이아몬드형 다중 경로를 만들지 않으므로 CLI 재현 예가 아닙니다.

| 노드 | 양방향 이웃 |
| --- | --- |
| s | b, a |
| a | s, t |
| b | s, t |
| t | a, b |

목적지 t까지의 거리는 t=0, a=1, b=1, s=2입니다. 두 경로 `s->a->t`, `s->b->t`는 모두 2간선입니다. 최단 거리를 유지하는 후보 중 a가 사전순으로 앞서므로 전자를 선택합니다. 사전순은 문자열의 앞에서부터 비교해 처음 다른 문자로 순서를 정하는 방식입니다.

hash 길이가 다르거나 접두 관계라면 구분자도 비교해야 합니다. 예를 들어 `a->`는 `a0->`보다 작습니다. 실제 함수는 구분자를 붙여 비교하고, 모든 최단 경로를 목록으로 만들지 않아 메모리를 절약합니다.

두 커밋이 연결되지 않으면 `No path`, 출발지와 목적지가 같으면 해당 hash 하나가 결과입니다. 존재하지 않는 hash는 탐색 전에 조회 오류로 구분합니다.

### 3-5. ANCESTORS는 DFS로 빠짐없이 방문한다

이 기능의 목적은 출발 커밋에 영향을 준 이전 기록을 빠짐없이 모으는 것입니다. 최단 거리는 필요하지 않으므로 부모를 스택에 넣고 DFS로 방문합니다.

- 시작 커밋 자체가 아니라 그 부모들을 스택에 넣습니다.
- 꺼낸 hash를 이미 방문했다면 건너뜁니다.
- 처음 본 hash는 결과와 방문 집합에 추가하고 그 부모들을 스택에 넣습니다.

복수 부모가 같은 조상을 공유해도 방문 집합이 중복 출력을 막습니다. 긴 커밋 체인에서도 Python 재귀 깊이에 의존하지 않습니다. 결과는 DFS 방문 순서이며 날짜순이나 부모 우선 전체 로그 순서가 아닙니다.

### 3-6. 역색인은 무엇을 뒤집는가?

검색할 때마다 모든 메시지를 읽으면 커밋이 늘어날수록 작업량이 커집니다. 현재 구현은 커밋 생성 시 단어별·작성자별 hash 목록을 갱신하고, 조회할 때 그 목록만 사용합니다.

설명용으로 메시지가 각각 `Add login`, `Add payment`라면 다음 색인을 만듭니다.

| 단어 | 커밋 hash 목록 |
| --- | --- |
| add | 00000002, 00000003 |
| login | 00000002 |
| payment | 00000003 |

`SEARCH login`은 00000002만 조회합니다. `SEARCH "add login"`은 더 짧은 login 목록을 기준으로 그 hash가 add 목록에도 있는지 확인합니다. 후보 목록을 집합으로 바꾸어 포함 여부를 검사하므로 변환 비용도 필요합니다.

메시지 안의 같은 단어는 중복 제거 후 등록하므로 `login login` 때문에 같은 커밋이 두 번 나오지 않습니다. 각 목록은 생성 순서로 저장되고 교집합 결과도 그 순서를 유지합니다. 작성자는 `Alice Kim`처럼 전체 이름을 키로 사용합니다.

정확한 토큰 검색은 부분 문자열 검색과 다릅니다. `login`은 `logging`을 찾지 않으며 구두점도 보존합니다. 검색이 빨라지는 대신 커밋을 생성할 때 등록 작업과 추가 저장 공간이 필요합니다.

### 3-7. 직접 구현한 안정 병합 정렬

옵션 LOG는 시각 또는 작성자를 비교 기준으로 삼아야 합니다. 현재 구현은 비교할 필드의 값을 꺼내는 `key`를 전달하고 직접 작성한 병합 정렬로 커밋을 재배치합니다.

합칠 때 `<`가 아니라 **`<=`**를 사용하므로 값이 같으면 왼쪽에 있던 항목을 먼저 고릅니다. 왼쪽은 원래 입력에서 앞에 있던 부분이므로 같은 작성자·같은 시각의 커밋도 생성 순서를 유지합니다.

| 방법 | 평균/최악 비교 횟수 | 안정성·선택 이유 |
| --- | --- | --- |
| 병합 정렬 | O(N log N) / O(N log N) | 이 구현은 안정적. 시간 예측이 쉽지만 추가 배열 필요 |
| 삽입 정렬 | 일반 무작위 입력 평균 O(N²), 최악 O(N²) | 안정적으로 구현 가능. 작은 입력·거의 정렬된 입력에 적합 |
| 퀵 정렬 | 무작위 피벗 등에서 기대 O(N log N), 최악 O(N²) | 일반적인 제자리 구현은 불안정. 분할 기준인 피벗 선택의 영향이 있음 |

여기서 N은 정렬 대상 커밋 수입니다. 병합 정렬만 구현했으며 이 표는 성능 측정 결과가 아니라 알고리즘의 이론 비교입니다.

### 3-8. 이 코드에서 사용한 Python 내장 함수

현재 프로젝트의 Python 소스에서 실제 호출한 내장 함수와 내장 타입 생성자입니다.

| 이름 | 기본 기능 | 이 미션에서의 용도 |
| --- | --- | --- |
| `len()` | 항목 수 확인 | 인자 개수, 병합 범위, 남은 부모 수, 처리·검색 건수 확인 |
| `getattr()` | 이름으로 객체 속성 조회 | 옵션 LOG에서 timestamp 또는 author 선택 |
| `min()` | 기준 값이 가장 작은 항목 선택 | 길이가 가장 짧은 검색 후보 목록 선택 |
| `all()` | 모든 조건이 참인지 확인 | 후보 hash가 모든 검색 단어의 집합에 있는지 검사 |
| `input()` | 한 줄 입력 읽기 | REPL에서 다음 명령 받기 |
| `print()` | 화면에 값 출력 | 커밋·경로·검색 결과와 오류 표시 |
| `list()` | 내장 타입 생성자: 목록 생성 | 부모·조회 결과 복사와 정렬 입력 준비 |
| `set()` | 내장 타입 생성자: 중복 없는 집합 생성 | 단어 중복 제거, 방문 기록과 검색 포함 여부 검사 |

`ValueError()`도 호출하지만 일반 계산 함수가 아니라 내장 예외 클래스의 생성자입니다. 잘못된 인자·없는 브랜치·없는 커밋·순환 등을 알릴 예외 객체를 만듭니다. `EOFError`와 `KeyboardInterrupt`는 종료 상황을 잡는 데 참조하며 직접 생성하지는 않습니다.

`dict`, `tuple`, `str`은 자료 표현이나 타입 표기에 등장하지만 생성자를 직접 호출하지 않습니다. `hash`라는 필드명이 있어도 내장 함수 `hash()`를 호출하는 것은 아닙니다. 공식 구분은 [Python 내장 함수 문서](https://docs.python.org/3/library/functions.html)에서 확인할 수 있습니다.

#### 메서드·표준 라이브러리·직접 만든 함수와 구분하기

문자열의 `lower()`·`split()`·`strip()`, 목록의 `append()`·`extend()`·`pop()`, 사전의 `get()`·`setdefault()`는 객체에 붙어 있는 메서드입니다. 내장 함수와 구분합니다.

`deque`·`shlex.split()`·`dataclass()`·`datetime.now()`는 표준 라이브러리에서 가져온 도구입니다. `min(..., key=len)`은 목록을 정렬하는 것이 아니라 최솟값 하나를 고르므로 표준 정렬 API를 사용한 것이 아닙니다.

`merge_sort()`·`topological_order()`·`find_ancestors()`·`shortest_path()`는 이 프로젝트에서 직접 작성한 함수입니다. 상세 호출 흐름과 줄별 문법은 [코드·명령 해설](code_translation.md)에서 확인하세요.

### 3-9. 시간·공간복잡도

시간복잡도는 입력이 늘 때 작업량이 어떻게 증가하는지, 공간복잡도는 필요한 저장 공간이 어떻게 증가하는지 나타냅니다. O(1)은 입력 수에 따른 작업량 증가가 일정하다는 뜻이며 시간이 전혀 들지 않는다는 뜻은 아닙니다.

V는 저장소 커밋 수, E는 부모 간선 수입니다. Va·Ea는 조상 탐색에서 만나는 조상과 부모 연결의 수, Vc·Ec는 목적지가 속한 연결 요소의 노드·간선 수입니다. 연결 요소는 양방향 연결을 따라 서로 도달할 수 있는 노드들의 묶음입니다.

K는 검색 결과/후보 수, Q는 중복 제거한 검색 단어 수, P는 그 단어들의 인덱스 목록 길이 합, M은 가장 짧은 목록 길이입니다. L은 메시지 길이, U는 그 메시지의 고유 단어 수, S는 검색 문자열 길이입니다.

아래는 딕셔너리·집합 조회의 평균 O(1), 목록 끝 추가의 분할상환 O(1), 짧은 hash·키 비교를 가정합니다. 분할상환은 목록의 가끔 발생하는 확장 비용을 여러 번의 추가 연산에 나누어 보는 관점이며 한 번의 추가가 언제나 같은 비용이라는 뜻은 아닙니다.

| 작업 | 시간 | 추가 공간·전제 |
| --- | --- | --- |
| 커밋 hash 조회 | 평균 O(1), 충돌이 심하면 최악 O(V) | 참조 반환 O(1) |
| 브랜치 생성·전환 | 평균 O(1) | 새 브랜치는 평균 O(1) 공간 |
| COMMIT·인덱싱 | 평균·분할상환 기준 O(L + U) | 토큰 임시 O(L), 새 인덱스 항목 O(U). 부모 최대 1 |
| LOG 기본 | O(V + E) | 남은 부모 수·큐·결과 O(V) |
| LOG 정렬 | O(V log V) | 병합 배열·슬라이스의 최대 동시 추가 공간 O(V), 재귀 스택 O(log V) |
| ANCESTORS | O(Va + Ea), 조상이 없으면 O(1) | 방문 집합·결과 O(Va), 중복 대기 항목을 포함한 스택 최악 O(Va + Ea) |
| PATH | O(Vc + Ec) | 거리·큐·결과 O(Vc). 경로를 고를 때 각 경로 노드의 이웃도 확인 |
| 한 단어 SEARCH | 평균 O(S + K) | 토큰과 후보 집합·결과 O(S + K) |
| 여러 단어 SEARCH | 평균 O(S + P + Q×M) | 토큰·후보 집합·결과 O(S + P + Q) |
| 작성자 SEARCH | 평균 O(S + K) | 결과 복사·커밋 목록 O(K) |

조회 과정의 딕셔너리·집합 충돌 최악 상황에서는 위 평균 기반 식보다 느려질 수 있습니다. 문자열 비교 비용까지 계산하려면 키 길이를 함께 고려해야 합니다. 화면 출력 시간도 출력 문자 수만큼 필요합니다. 정렬 비교 횟수와 전체 문자 처리 비용은 구분하세요.

현재 PATH는 출발점을 찾았다고 BFS를 바로 멈추지 않고 목적지가 속한 연결 요소를 모두 탐색합니다. 두 커밋이 연결되지 않았을 때도 목적지 쪽 탐색 비용은 발생합니다.

저장소는 커밋·간선·브랜치·역색인 항목·메시지 문자열을 보관합니다. 키워드 하나가 모든 메시지에 들어가면 결과 자체가 V개이므로 역색인이 있어도 출력까지 O(1)이 될 수 없습니다.

## 4. 질문 테스트

다음 질문은 본문의 개념을 스스로 확인하기 위한 학습 문제입니다. 먼저 답을 생각한 뒤 아래 정답·해설을 펼쳐 보세요.

### 질문 A. 브랜치와 경로의 결과 예상하기


PATH의 결과와 LOG의 메시지 순서는 무엇인가요? 마지막 COMMIT 직후 main과 work는 각각 어느 커밋을 가리키나요?

### 질문 B. 커밋 생성 전후의 상태 추적하기

위 예의 `COMMIT fix` 직전과 직후를 비교해 보세요. 현재 브랜치, main의 위치, 새 커밋의 부모, fix 단어의 역색인 목록은 어떻게 달라지나요? work의 위치도 함께 이동하나요?

### 질문 C. 탐색과 위상 정렬의 선택 이유 설명하기

1. PATH에서 일반적인 DFS의 첫 발견 경로를 그대로 쓰면 최단 경로를 보장할 수 있을까요?
2. 칸 알고리즘에서 부모가 두 개인 커밋은 부모 하나를 출력한 즉시 큐에 넣어도 될까요?
3. BFS와 칸 알고리즘이 모두 큐를 쓰는데도 서로 다른 문제를 푸는 이유는 무엇인가요?

### 질문 D. 검색 결과 예상하기

메시지가 각각 `Add LOGIN`, `add payment`, `login, guide`인 세 커밋이 이 순서로 있습니다. `SEARCH login`, `SEARCH "ADD login"`, `SEARCH log`는 각각 무엇을 찾을까요? 첫 메시지가 `Add LOGIN login`이면 같은 커밋이 두 번 나올까요?

### 질문 E. 정렬과 내장 함수 구분하기

1. 작성자가 같은 커밋 두 개를 옵션 LOG로 정렬할 때 기존 순서가 유지되는 이유는 무엇인가요?
2. `min(postings, key=len)`은 후보 목록들을 정렬하나요? `min()`·`len()`과 `append()`는 각각 어떤 종류의 도구인가요?

**A.** PATH는 `00000002 → 00000001 → 00000003`, LOG의 메시지 순서는 `root, task, fix`입니다. root를 공유하는 두 자식이 task, fix 순서로 큐에 들어갑니다. main은 00000003, work는 00000002를 가리킵니다.

## 5. 확장해 볼 부분

다음은 필수 범위를 이해한 뒤 별도 복사본에서 시도할 선택 학습입니다. 현재 구현된 기능이나 추가 필수 제출물로 해석하지 않습니다.

### 검색 결과가 없을 때 안내 문구 추가하기

- 목표: 조회 기능을 유지하면서 사용자 안내를 개선합니다.
- 시작점: `main.py`의 `handle_search()`에서 결과를 받은 뒤 개수를 확인합니다.
- 확인할 결과: 결과가 없을 때만 `검색어를 확인하세요.`를 한 번 표시하고 정상 검색 결과는 기존과 같게 유지합니다.

### 두 부모를 가진 커밋과 공통 조상 알아보기

- 목표: 갈라진 두 이력을 합칠 때 부모 관계가 어떻게 바뀌는지 이해합니다.
- 시작점: `repository.py`의 커밋 생성과 `parents` 모델을 읽고 두 부모를 갖는 설명용 그래프를 먼저 그립니다.
- 확인할 결과: ANCESTORS에서 공유 조상이 한 번만 나오고 LOG에서 두 부모 모두 합친 커밋보다 먼저 나오는지 설명합니다. 명령을 추가한다면 자식·이웃 목록과 역색인 갱신도 함께 설계합니다.

### 검색 토큰의 구두점 처리 개선하기

- 목표: `login`과 `login,`을 같은 단어로 볼지 검색 정책을 정합니다.
- 시작점: `index.py`에서 등록과 검색에 쓰는 토큰화 규칙을 같은 방식으로 바꿉니다.
- 확인할 결과: 대소문자·구두점·여러 단어·중복 단어 사례에서 정한 규칙대로 찾고 작성자 전체 이름 검색은 의도한 정책을 유지합니다. 한국어 형태소 분석은 그 이후의 별도 주제입니다.

### 종료 후에도 이력 보존하기

- 목표: 메모리의 기록을 파일에 저장하고 다음 실행에서 복구합니다.
- 시작점: 커밋·브랜치·현재 위치·다음 식별자의 저장 형식을 정하고 역색인과 이웃 목록은 로드 후 재구성할지 검토합니다.
- 확인할 결과: 재시작 후 기존 커밋을 찾고 새 식별자가 겹치지 않아야 합니다. 일부만 기록된 파일과 잘못된 부모 참조를 어떻게 처리할지도 정합니다.

### 커밋 삭제 시 역색인 정리하기

- 목표: 원본 기록과 검색 후보가 어긋나지 않도록 갱신 규칙을 설계합니다.
- 시작점: `index.py`의 등록 흐름을 읽고 삭제된 hash를 단어·작성자 목록에서 제거할 방법을 정합니다.
- 확인할 결과: 검색 결과에 없는 커밋을 가리키는 hash가 남지 않아야 합니다. 부모·자식·브랜치가 삭제 대상을 참조할 때의 처리 정책도 함께 정합니다. 현재는 삭제 명령이 없으므로 이 작업이 필요하지 않습니다.

실제 Git으로 학습을 이어가려면 파일 스냅샷·내용 기반 해시·압축 객체 저장도 살펴보세요. 커밋 정보와 관계를 보존하는 것에서 실제 파일 내용을 보존하는 것으로 학습 범위를 넓히는 주제입니다.
