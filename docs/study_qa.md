### 1. INIT는 무엇을 설정하며, 초기화를 다시 요청하면 어떻게 해야 하나요?

**핵심 답변:** 작성자와 main 브랜치를 설정하고, 아직 커밋이 없는 상태로 시작합니다.

`INIT Kim` 직후의 상태는 다음과 같습니다.

| 항목 | 값 | 의미 |
| --- | --- | --- |
| `user` | `Kim` | 이후 커밋의 작성자 |
| `current_branch` | `main` | 현재 작업할 브랜치 |
| `branches['main']` | `None` | 아직 가리킬 커밋이 없음 |

초기화 전에는 저장소를 변경하거나 조회할 수 없습니다. 현재 구현은 두 번째 INIT를 `Repository already initialized`로 거부합니다. 기존 기록을 실수로 지우지 않기 위한 선택입니다. 빈 저장소로 다시 시작하려면 종료 후 재실행합니다.

RESET은 현재 없는 확장 기능입니다. 추가한다면 사용자·브랜치·커밋·그래프·인덱스·카운터를 함께 초기화해야 합니다.

코드에서 확인: [repository.py](../repository.py)의 `initialize`, `require_initialized`.

### 2. BRANCH, SWITCH, COMMIT은 각각 어떤 상태를 바꾸나요?

**핵심 답변:** BRANCH는 위치에 이름을 붙이고, SWITCH는 현재 이름을 바꾸며, COMMIT은 새 기록을 만들고 현재 브랜치를 이동시킵니다.

| 명령 | 바뀌는 상태 | 유지되는 상태 |
| --- | --- | --- |
| `BRANCH feature` | 새 브랜치가 현재 hash를 가리킴 | 현재 브랜치와 기존 커밋 |
| `SWITCH feature` | `current_branch` | 커밋·작성자·각 브랜치의 hash |
| `COMMIT second` | 커밋·그래프·역색인·현재 브랜치의 hash·카운터 | 다른 브랜치의 hash |

main과 feature가 모두 00000001을 가리킬 때 feature로 전환해 커밋하면, feature만 00000002로 이동합니다. 새 커밋의 부모는 00000001입니다. 브랜치를 만들 때 과거 커밋을 복사하지는 않습니다.

코드에서 확인: [repository.py](../repository.py)의 `create_branch`, `switch_branch`, `commit`.

### 3. 칸 알고리즘은 어떻게 부모를 먼저 출력하며, 옵션 정렬과는 어떤 관계인가요?

**핵심 답변:** 아직 출력하지 않은 부모가 하나도 없는 커밋만 다음 출력 대상으로 선택합니다.

칸(Kahn) 알고리즘의 흐름은 다음과 같습니다.

1. 각 커밋의 남은 부모 수를 셉니다.
2. 그 수가 0인 커밋을 큐에 넣습니다.
3. 하나를 꺼내 출력 순서에 추가하고, 각 자식의 남은 부모 수를 1 줄입니다.
4. 남은 부모 수가 0이 된 자식을 큐에 넣고 반복합니다.

A가 B와 C의 부모라면 A를 처리한 뒤에야 B와 C가 후보가 됩니다. 부모가 두 개인 커밋은 두 부모가 모두 처리되어야 후보가 됩니다.

기본 LOG는 이 규칙을 사용합니다. 옵션 LOG는 날짜 또는 작성자 기준으로 전체를 따로 정렬하므로 부모 우선을 추가로 보장하지 않습니다. 두 규칙을 결합하려면 현재 출력 가능한 후보들 안에서만 다음 항목을 골라야 하는데, 현재 구현은 그 방식이 아닙니다.

코드에서 확인: [algorithms.py](../algorithms.py)의 `topological_order`, [repository.py](../repository.py)의 `log`.

### 4. 최단 경로가 여러 개라면 무엇을 선택하며, 왜 구분자까지 비교하나요?

**핵심 답변:** 최소 간선 수의 경로들 중 공백 없는 `hash1->hash2->...` 문자열이 사전순으로 가장 앞서는 경로를 선택합니다.

예를 들어 `s->a->t`와 `s->b->t`가 모두 2간선이면 a가 b보다 앞서므로 첫 경로를 고릅니다. 이 예는 알고리즘에 별도로 주는 설명용 그래프입니다. 부모가 최대 하나인 현재 COMMIT만으로는 이런 다중 경로를 만들지 못합니다.

실제 선택 과정은 다음과 같습니다.

1. 목적지에서 BFS로 각 노드의 거리를 구합니다.
2. 출발지에서 거리가 1 줄어드는 이웃만 남깁니다.
3. 그중 `neighbor + '->'`가 가장 작은 것을 골라 이어갑니다.

hash가 접두 관계라면 구분자도 문자열 비교에 영향을 줍니다. 예를 들어 `a->`는 `a0->`보다 앞섭니다. 비교에 쓰는 화살표에는 공백이 없고, 화면의 ` -> ` 공백은 읽기 편하게 넣은 것입니다.

코드에서 확인: [algorithms.py](../algorithms.py)의 `shortest_path`, [main.py](../main.py)의 `handle_path`.

### 5. ANCESTORS는 모든 조상을 어떻게 중복 없이 찾고, 어떤 순서로 돌려주나요?

**핵심 답변:** 부모 방향으로 DFS를 수행하고, 방문 집합으로 중복을 막습니다. 결과는 DFS 방문 순서입니다.

시작 커밋의 부모들만 스택에 넣으므로 자기 자신은 결과에 포함하지 않습니다. 스택에서 꺼낸 hash가 이미 방문한 대상이면 건너뜁니다. 처음 만난 조상은 결과에 넣고 그 부모들을 스택에 추가합니다.

설명용으로 D의 부모가 `(B, C)`이고 B와 C의 부모가 모두 A라면, 초기 스택은 `[B, C]`입니다. 오른쪽에서 꺼내므로 `C → A → B` 순서로 방문하고, B에서 다시 만나는 A는 건너뜁니다.

이 복수 부모 예는 알고리즘 입력용입니다. 현재 COMMIT은 부모가 최대 하나입니다. 재귀 대신 스택을 쓰므로 긴 이력에서도 재귀 깊이 한도에 의존하지 않으며, 결과를 날짜순이나 위상 순서로 다시 정렬하지는 않습니다.

코드에서 확인: [algorithms.py](../algorithms.py)의 `find_ancestors`, [repository.py](../repository.py)의 `ancestors`.

### 6. 키워드 검색, 작성자 검색, LOG 정렬 옵션은 어떻게 구분하나요?

**핵심 답변:** 명령의 옵션을 먼저 구분하고, 검색은 해당 역색인에, 정렬은 비교 기준을 바꾼 병합 정렬에 맡깁니다.

| 입력 예 | 처리 기준 |
| --- | --- |
| `SEARCH login` | 소문자·공백 단위 메시지 토큰 |
| `SEARCH "add login"` | 두 단어를 모두 가진 커밋: AND 검색 |
| `SEARCH --author="Alice Kim"` | 작성자 전체 이름, 대소문자까지 일치 |
| `LOG --sort-by=date` | timestamp 오름차순 |
| `LOG --sort-by=author` | 작성자 문자열 오름차순 |

`login`은 `LOGIN`과 같게 보지만 `log`, `logging`, `login,`과는 다른 토큰입니다. 현재는 구두점을 자동 제거하지 않습니다. 옵션 정렬은 안정적이므로 기준 값이 같으면 기존 생성 순서를 유지합니다. 지원하지 않는 정렬 값은 `Invalid args`입니다.

여러 단어를 AND로 결합하는 방식, 작성자 대소문자 구분, 오름차순과 안정성은 현재 구현이 정한 정책입니다. 모두 원문이 상세하게 지정한 규칙인 것은 아닙니다.

코드에서 확인: [main.py](../main.py)의 `handle_search`, `handle_log`와 [repository.py](../repository.py)의 `search`, `log`.

### 7. HEAD, 브랜치, 커밋 저장소는 왜 분리하나요?

**핵심 답변:** 현재 작업 위치와 이름별 위치, 실제 기록을 나누면 브랜치를 옮길 때 기록 자체를 복사할 필요가 없습니다.

현재 구현의 조회 흐름은 `current_branch → branches의 hash → commits의 커밋 객체`입니다. 예를 들어 현재 이름이 feature이고 그 이름이 00000002를 가리키면 현재 커밋은 00000002입니다.

COMMIT에서는 현재 이름을 유지하면서 그 이름의 hash만 옮깁니다. SWITCH에서는 현재 이름을 바꿉니다. HEAD에 hash까지 중복 저장할 때 생길 수 있는 갱신 불일치를 줄이는 구조입니다.

실제 Git의 detached HEAD처럼 브랜치를 거치지 않고 커밋을 직접 가리키는 상태는 구현하지 않았습니다.

코드에서 확인: [repository.py](../repository.py)의 `Repository`, `switch_branch`, `commit`.

### 8. 커밋 식별자는 어떻게 만들며, 중복과 해시 충돌은 어떻게 다른가요?

**핵심 답변:** 카운터로 식별자를 발급하고 dict로 조회합니다. 같은 식별자의 재발급과 dict 내부의 해시 충돌은 별개입니다.

| 구분 | 의미 | 현재 처리 |
| --- | --- | --- |
| 식별자 중복 | 같은 hash 문자열을 다시 발급 | 정상 API에서는 카운터를 재사용하지 않음 |
| 해시 충돌 | 서로 다른 dict 키의 내부 해시값이 같음 | dict가 키의 동등성도 확인해 구별 |

식별자는 최소 8자리 16진수이며 `00000009` 다음은 `0000000a`입니다. 자리수가 늘어나도 잘라내지 않습니다. 내용 기반 암호학적 해시는 아닙니다.

현재 보장은 정상 API 사용을 전제로 합니다. 외부에서 카운터를 되돌리는 일을 막는 별도 검사는 없으므로 임의로 변경하면 기존 항목을 덮어쓸 수 있습니다.

코드에서 확인: [repository.py](../repository.py)의 `__init__`, `commit`, `get_commit`.

### 9. 역색인은 언제 갱신하며, 갱신 도중 실패하면 어떤 문제가 생기나요?

**핵심 답변:** 커밋 생성 시 단어와 작성자 색인을 함께 갱신해야 검색 결과와 원본 기록이 일치합니다.

같은 메시지의 같은 단어는 한 번만 등록합니다. `Add LOGIN login`은 소문자 토큰 add와 login으로 정리되고, 각 목록에 해당 hash를 한 번씩 추가합니다.

현재 처리 순서는 `카운터 증가 → 커밋·그래프 등록 → 역색인 갱신 → 현재 브랜치 이동`입니다. 도중에 실패하면 앞선 변경만 남을 수 있습니다. 예를 들어 색인 갱신이 실패하면 커밋은 있지만 현재 브랜치는 이전 위치에 남을 수 있습니다.

여러 변경을 한꺼번에 반영하거나 모두 취소하는 성질을 원자성이라고 합니다. 현재 구현에는 이런 롤백이 없습니다. 임시 상태에 변경을 준비한 뒤 함께 반영하거나, 실패 시 앞선 변경을 취소하는 방법은 개선 방향입니다.

코드에서 확인: [repository.py](../repository.py)의 `commit`, [index.py](../index.py)의 `add`.

### 10. 알고리즘을 별도 모듈로 나누면 무엇이 좋고, 입력·출력 계약은 무엇인가요?

**핵심 답변:** 작은 데이터로 알고리즘만 검증하고 재사용할 수 있습니다. 계약은 받을 입력, 돌려줄 결과와 오류 조건의 약속입니다.

| 함수 | 받는 입력 | 반환과 전제 |
| --- | --- | --- |
| `merge_sort` | 슬라이싱 가능한 목록과 비교 키 | 새 정렬 목록. 키끼리 비교할 수 있어야 함 |
| `topological_order` | 커밋 매핑과 자식 목록 | 부모 우선 hash 목록. 일관된 그래프를 전제로 순환 시 오류 |
| `find_ancestors` | 커밋 매핑과 시작 hash | 자기 자신을 제외한 조상. 유효한 부모 참조와 DAG 전제 |
| `shortest_path` | 대칭인 무방향 이웃 목록과 두 hash | 양 끝점을 포함한 경로. 연결되지 않으면 빈 목록 |

입력 인접 목록이나 원본 커밋의 부모를 바꾸지 않고 보조 자료를 만들어 처리합니다. 다만 병합 정렬의 반환 목록에 들어 있는 커밋 객체까지 깊게 복사하는 것은 아닙니다.

없는 hash를 사용자 오류로 처리하는 일은 Repository가, 화면에 표시하는 일은 CLI가 맡습니다. 알고리즘 함수를 직접 호출할 때도 같은 검증이 자동 적용된다고 가정하면 안 됩니다.

코드에서 확인: [algorithms.py](../algorithms.py), [repository.py](../repository.py)의 호출부.

### 11. docstring에는 무엇을 설명하며, 사용 예시는 왜 필요한가요?

**핵심 답변:** 호출하는 사람이 알아야 할 목적·입력·반환·전제·오류·순서 규칙을 적습니다.

코드의 각 줄을 다시 말하기보다 “무엇을 전달하면 어떤 결과를 받는가”를 먼저 설명해야 합니다. 예시는 그 약속을 실제 값과 연결합니다.

다음은 현재 함수를 사용하는 설명용 예시이며 소스의 docstring을 수정한 것은 아닙니다.

```python
merge_sort([3, 1, 2], key=lambda value: value)
# 결과: [1, 2, 3]

shortest_path({'A': ['B'], 'B': ['A', 'C'], 'C': ['B']}, 'A', 'C')
# 결과: ['A', 'B', 'C']
```

조상 조회라면 시작점을 제외하는지와 방문 순서를, 최단 경로라면 동률 선택 규칙을 함께 알려 주면 결과를 예측하기 쉽습니다.

코드에서 확인: [algorithms.py](../algorithms.py)의 모듈·함수 docstring.

<a id="q12"></a>

### 12. 순환 검출과 커밋 불변성은 각각 왜 필요한가요?

**핵심 답변:** 순환 검출은 잘못된 관계를 발견하고, 불변성은 이미 만든 기록의 변경을 제한합니다.

칸 알고리즘에서 출력한 노드 수가 전체보다 적으면 남은 노드들이 선행 관계 때문에 처리되지 못한 것이므로 `Cycle detected` 오류를 냅니다. 이 판단은 부모 목록과 자식 목록이 일치하는 그래프를 전제로 합니다. 자료구조가 어긋난 경우까지 같은 원인으로 단정하지 않습니다.

`@dataclass(frozen=True)`는 일반적인 필드 재대입을 막고, 부모 tuple은 항목 수정을 막습니다. 정상 COMMIT은 기존 기록을 수정하지 않고 새 노드가 기존 부모만 참조하게 하므로 순환을 만들지 않습니다.

저장소의 dict와 인접 목록까지 불변인 것은 아닙니다. 기존 기록의 변경 제한, 정상 생성 규칙, 그래프의 일관성은 함께 고려해야 합니다.

코드에서 확인: [repository.py](../repository.py)의 `Commit`, [algorithms.py](../algorithms.py)의 `topological_order`.

### 13. 기본 LOG가 보장하는 출력 순서는 정확히 무엇인가요?

**핵심 답변:** 현재 브랜치만이 아닌 전체 저장소에서 모든 부모가 자식보다 먼저 나옵니다.

A에서 B와 C로 갈라졌다면 A는 반드시 먼저 나와야 합니다. B와 C 사이에는 선행 관계가 없으므로 부모 우선 조건만으로 유일한 순서가 정해지지는 않습니다. 현재 구현은 준비 큐에 들어온 순서를 따릅니다.

기본 LOG를 전체 생성 순서나 날짜순과 같은 뜻으로 설명하면 안 됩니다. 옵션 LOG는 별도 기준 정렬이며, 둘의 차이는 [3번](#q3)을 참고하세요.

<a id="q14"></a>

### 14. PATH는 왜 무방향 그래프에서 BFS를 쓰며, 예외 상황은 어떻게 구분하나요?

**핵심 답변:** 부모와 자식 양쪽 이동을 허용하고 모든 간선 비용이 같으므로 BFS로 최소 간선 수를 구합니다.

B와 C가 A에서 갈라졌다면 B에서 C로 가려면 `B → A → C`로 이동해야 합니다. 부모로 올라가는 방향만 탐색하면 C에 도달할 수 없습니다. 일반 그래프에서 DFS의 첫 발견 경로가 최단이라는 보장은 없습니다.

| 상황 | 내부 결과 | CLI 표시 |
| --- | --- | --- |
| 서로 연결됨 | 양 끝점을 포함한 경로 | `Path: ...` |
| 존재하지만 서로 연결되지 않음 | 빈 목록 | `No path` |
| 출발점과 목적지가 같음 | 해당 hash 하나 | `Path: 해당 hash` |
| hash가 존재하지 않음 | 검증 단계에서 예외 | `Unknown commit: ...` |

목적지에서 거리표를 만든 뒤 출발지에서 거리가 1씩 줄어드는 이웃으로 경로를 복원합니다. 동률 선택은 [4번](#q4)의 규칙을 사용합니다.

코드에서 확인: [repository.py](../repository.py)의 `path`, [algorithms.py](../algorithms.py)의 `shortest_path`.

<a id="q15"></a>

### 15. 직접 구현한 병합 정렬은 왜 안정적이며, 시간·공간복잡도는 얼마인가요?

**핵심 답변:** 동률이면 왼쪽 항목을 먼저 골라 원래 순서를 보존합니다. 시간은 O(n log n), 최대 추가 공간은 O(n)입니다.

목록을 반으로 나눠 각각 정렬하고 작은 항목부터 합칩니다. 같은 키끼리는 `<=` 조건으로 왼쪽을 먼저 선택합니다. `sorted()`나 `list.sort()`로 대체하지 않습니다.

각 분할 깊이의 병합 작업을 모두 합하면 O(n)이고, 깊이는 O(log n)이므로 전체는 O(n log n)입니다. 현재 방식은 이미 정렬된 입력도 계속 나누므로 최선·평균·최악이 모두 같은 차수입니다.

슬라이스와 병합 배열의 최대 동시 추가 공간은 O(n), 재귀 깊이는 O(log n)입니다. 분석은 키 계산과 비교 비용을 일정하게 본 결과입니다.

코드에서 확인: [algorithms.py](../algorithms.py)의 `merge_sort`.

<a id="q16"></a>

### 16. 역색인의 어떤 연산이 평균 O(1)이며, 전체 검색은 얼마나 걸리나요?

**핵심 답변:** 단어·작성자로 후보 목록을 찾는 키 조회가 평균 O(1)입니다. 후보 처리와 결과 생성까지 상수 시간은 아닙니다.

여러 단어를 검색할 때는 다음 비용이 생깁니다.

1. 각 단어의 후보 목록을 가져옵니다.
2. 그 목록들을 set으로 바꿉니다.
3. 가장 짧은 목록의 각 hash가 모든 set에 있는지 확인합니다.
4. 남은 hash에 해당하는 커밋을 조회합니다.

고유 단어 수를 k, 후보 목록 길이를 Lᵢ, 가장 짧은 길이를 m이라 하면 토큰화 이후 평균 시간은 `O(k + ΣLᵢ + k×m)`입니다. 문자열 처리 비용도 포함하려면 검색어 길이 s에 대한 비용을 더해야 합니다.

한 단어 또는 작성자 검색에서 결과가 r개이면 키·문자열 처리 비용을 별도로 볼 때 `O(r + 1)`입니다. 현재 한 단어 검색도 후보 집합을 만드므로 임시 공간을 사용합니다. 전체 커밋을 다시 훑지는 않습니다.

코드에서 확인: [index.py](../index.py)의 `search_keyword`, `search_author`와 [repository.py](../repository.py)의 `search`.

### 17. 데이터가 많아지면 어디가 병목이며, 어떻게 개선할 수 있나요?

**핵심 답변:** 전체 이력 조회, 긴 후보 목록의 집합 변환, 모든 데이터를 보관하는 메모리가 병목이 될 수 있습니다.

기본 LOG는 O(V + E), 옵션 LOG는 O(V log V)입니다. PATH는 목적지가 속한 연결 요소 전체를 BFS로 확인하므로 최악 O(V + E)입니다. 가까운 출발점을 발견했다고 즉시 멈추는 구현은 아닙니다.

흔한 단어의 검색 후보가 많으면 집합 변환과 결과 생성 비용도 커집니다. 저장 공간에는 커밋·간선·브랜치·색인 항목뿐 아니라 메시지·키 문자열도 필요합니다.

정렬된 후보 목록의 교집합, 비트맵, 반복 조회 캐시, 영속 저장, 페이지 단위 출력은 개선 방향입니다. 여러 장비로 색인을 나누는 분산 처리까지 도입하면 갱신 일관성과 결과 결합도 설계해야 합니다. 현재 구현된 기능이나 원문의 필수 요구사항은 아닙니다.

코드에서 확인: [repository.py](../repository.py)의 저장 구조와 [index.py](../index.py)의 후보 처리.

### 18. 카운터와 난수 식별자는 재현성과 검증에 어떤 차이를 만드나요?

**핵심 답변:** 카운터는 같은 순서에서 같은 식별자를 예측하기 쉽고, 난수는 충돌과 결과 통제를 별도로 고려해야 합니다.

현재는 새 저장소에서 같은 명령 순서를 실행하면 같은 hash와 부모 관계가 나옵니다. 하지만 timestamp는 현재 시각이므로 전체 출력까지 같지는 않습니다. 검증할 때는 구조와 시각을 구분해야 합니다.

난수로 바꾸면 충돌 검사·재시도가 필요합니다. 검증에서는 생성기를 외부에서 전달해 결과를 통제하거나 반환된 식별자로 관계를 확인할 수 있습니다. 이는 현재 카운터 방식의 대안입니다.

세션마다 다시 시작하는 카운터는 여러 저장소를 합칠 때의 전역 유일성을 보장하지 않습니다.

### 19. [과제 목표 1] 커밋 그래프는 어떻게 표현하며, 왜 DAG인가요?

**핵심 답변:** 커밋을 노드, 부모 참조를 방향 간선으로 표현합니다. 새 노드가 기존 부모만 가리키므로 순환 없이 이력을 이어갑니다.

각 커밋은 hash·message·author·timestamp·parents를 가집니다. 현재 구현은 커밋 저장소와 자식 목록, PATH용 양방향 이웃 목록을 나누어 보관합니다.

부모를 따라갈 때마다 먼저 만들어진 기록으로 이동하고 기존 부모 관계를 바꾸지 않으므로 새 커밋으로 돌아올 수 없습니다. 이 성질은 timestamp가 정확한지와는 무관합니다. 분기는 한 부모의 여러 자식, 병합은 한 커밋의 여러 부모로 표현할 수 있습니다.

부모 참조는 자식→부모, 부모 우선 출력의 보조 연결은 부모→자식 방향입니다. 방향을 뒤집어도 순환이 없다는 성질은 유지됩니다. 현재 CLI의 MERGE와 실제 파일 내용 추적은 구현하지 않았습니다.

<a id="q20"></a>

### 20. [과제 목표 2] 부모가 먼저 출력되는 로그에 왜 위상 정렬이 필요한가요?

**핵심 답변:** 날짜나 이름의 대소가 아니라 선행 관계를 지켜야 하기 때문입니다.

모든 부모가 자식보다 먼저라는 부분적인 조건을 만족하는 전체 나열을 위상 순서라고 합니다. 작성자순은 관계를 반영하지 않고, 날짜순도 시계 변화 등이 있으면 일반적으로 선행 관계를 보장하지 못합니다.

현재 칸 알고리즘은 남은 부모 수가 0인 노드만 골라 각 노드와 간선을 처리하므로 O(V + E)입니다. 독립된 커밋들의 순서는 여러 개가 가능하며 현재는 큐 순서를 사용합니다.

<a id="q21"></a>

### 21. [과제 목표 3] 최단 경로와 모든 조상은 어떻게 다르게 탐색하나요?

**핵심 답변:** PATH는 양방향 연결에서 BFS로 한 최단 경로를, ANCESTORS는 부모 방향에서 DFS로 모든 조상을 구합니다.

| 비교 | PATH | ANCESTORS |
| --- | --- | --- |
| 입력 | 출발점·목적지 | 시작 커밋 하나 |
| 이동 방향 | 부모·자식 양쪽 | 부모 쪽만 |
| 반환 | 최단 경로 하나, 동률은 사전순 | 모든 조상, 중복 제외 |
| 시작점 포함 | 경로의 한 끝점으로 포함 | 제외 |
| 대기 구조 | 큐 | 스택 |

A의 자식이 B와 C이면 B에서 C로 가는 경로는 `B → A → C`이고 B의 조상은 A뿐입니다. 형제 C를 조상에 넣지 않습니다.

최악 탐색 시간은 O(V + E)이며 조상 탐색은 도달 가능한 조상 부분만 봅니다. 복수 부모의 스택에 중복 대기 항목이 생길 수 있으므로 공간 분석에는 노드뿐 아니라 간선 수도 고려합니다.

<a id="q22"></a>

### 22. [과제 목표 4] 정렬 원리·평균/최악 복잡도·안정성을 어떻게 설명하나요?

**핵심 답변:** “반으로 나누고, 각각 정렬하고, 앞 항목을 비교해 합친다”는 원리와 동률 선택 규칙을 연결하면 됩니다.

분할 깊이 O(log n)마다 총 O(n)을 병합하므로 평균·최악 모두 O(n log n)입니다. 현재 구현은 최선도 같은 차수이며 최대 추가 공간은 O(n), 재귀 깊이는 O(log n)입니다. 키 계산·비교 비용은 일정하다고 가정합니다.

작성자가 같은 X와 Y가 X, Y 순서로 들어오면 정렬 후에도 이 순서가 유지되어야 안정적입니다. 병합 중 동률이면 왼쪽 항목을 먼저 고르는 것이 이 성질을 지킵니다.

선택 이유는 최악 시간의 예측 가능성과 안정성입니다. 추가 배열이 필요하다는 비용도 함께 설명해야 합니다. 다른 정렬을 실제로 구현하거나 측정한 것은 아닙니다.

<a id="q23"></a>

### 23. [과제 목표 5] 역색인은 왜 순회 검색보다 빠를 수 있나요?

**핵심 답변:** 모든 메시지를 다시 읽는 대신 미리 등록한 후보 목록만 확인하기 때문입니다.

`login → [00000002, 00000005]`가 있으면 다른 커밋 메시지를 읽지 않고 두 후보를 조회합니다. 작성자도 같은 방식입니다.

전체 메시지 길이 합을 T라 할 때 매번 모두 읽는 방식은 O(T)입니다. 단일 단어의 역색인 조회는 문자열 비용을 별도로 보면 평균 O(1)에 후보를 찾고 결과 r개에 O(r)을 사용합니다. 여러 단어는 교집합 비용이 추가되며 식은 [16번](#q16)에 있습니다.

대신 커밋 생성 때 색인을 만들 시간과 후보 목록을 저장할 공간을 부담합니다. 모든 커밋에 등장하는 단어라면 r이 V에 가까워지므로 전체 검색이 항상 상수 시간인 것은 아닙니다.

```text
QUIT
```

앞의 네 명령은 정상 처리되고, 두 검색은 첫 커밋을 한 번씩 찾습니다. 빈 메시지와 지원하지 않는 정렬 값은 `Invalid args`, 없는 브랜치는 `Unknown branch: missing`입니다. 그 뒤 LOG가 기존 커밋을 보여 주면 오류 후에도 REPL과 기존 기록이 유지되는 것을 확인할 수 있습니다.

명령어만 대소문자를 구분하지 않습니다. 작성자를 alice kim으로 검색하거나 브랜치 Main으로 전환하면 기존 이름과 다른 값입니다. `SEARCH --author=`는 빈 작성자이므로 `Invalid args`입니다. 따옴표가 닫히지 않은 입력도 같은 오류로 처리합니다.

원문 근거: 3쪽 CLI 공통 규칙. 오류 뒤 REPL 유지와 빈 인자 처리의 세부 정책은 현재 코드 기준입니다.

### 실습 2. 커밋이 없거나 이력이 연결되지 않은 경우 구분하기

첫 커밋 전에 브랜치를 하나 더 만들면 독립된 루트 두 개를 만들 수 있습니다. 새 실행에서 확인하세요.

```text
INIT Kim
LOG
BRANCH other
COMMIT first
SWITCH other
COMMIT second
PATH 00000001 00000002
PATH 00000001 00000001
ANCESTORS 00000001
PATH 00000001 missing
QUIT
```

| 확인할 지점 | 현재 구현의 예상 결과 | 이유 |
| --- | --- | --- |
| 첫 LOG | `No commits` | 아직 기록이 없음 |
| 두 루트 사이 PATH | `No path` | 서로 연결된 간선이 없음 |
| 같은 커밋 사이 PATH | `Path: 00000001` | 거쳐야 할 간선이 0개 |
| 루트의 ANCESTORS | `No commits` | 부모·조상이 없음 |
| 없는 hash를 포함한 PATH | `Unknown commit: missing` | 연결 탐색 전에 존재 검증 |

빈 결과의 문구와 동일 끝점 처리는 현재 구현 기준입니다. 원문은 PATH의 무방향 최소 간선 경로와 연결되지 않을 때의 `No path`를 명시합니다(4쪽). 조상 조회의 필수 조건은 모든 조상을 빠짐없이 찾는 것입니다(5쪽).

### 실습 3. CLI 예제와 알고리즘 입력 검증을 구분하기

| 확인하려는 동작 | 적절한 확인 방법 |
| --- | --- |
| 브랜치 분기·형제 사이 PATH | 현재 CLI 명령으로 실행 |
| 최단 경로가 여럿일 때 사전순 선택 | 다중 경로가 있는 이웃 목록을 `shortest_path`에 전달 |
| 복수 부모가 공유하는 조상 중복 제거 | 부모가 둘인 커밋 모델로 `find_ancestors` 확인 |
| 순환 검출 | 부모·자식 목록이 일치하는 순환 그래프를 `topological_order`에 전달 |
| 서로 다른 작성자의 정렬 | 작성자를 달리한 모델을 정렬 함수에 전달 |

현재 CLI에는 MERGE나 사용자 변경 명령이 없습니다. INIT 후 작성자는 고정되므로 모든 커밋이 같은 작성자를 가집니다. CLI에서 정렬 옵션이 실행되는 것과 서로 다른 작성자에 대한 정렬 정확성을 확인하는 것은 별개입니다.

기초 문서의 다이아몬드 경로·복수 부모 예는 알고리즘 설명용입니다. 명령 입력만으로 그대로 재현되는 사례로 읽지 마세요.

| 필수 자료구조 | 커밋 필드 5개, DAG, 세션 내 유일 hash, hash 기반 조회 | 원문 3쪽 |

### 선택 과제는 무엇부터 하면 좋을까요?

원문 5쪽의 보너스는 다음 세 가지입니다. 현재는 모두 미구현입니다.

| 선택 과제 | 배우는 내용 | 확장 시 확인할 점 |
| --- | --- | --- |
| 줄 단위 Diff | 두 파일의 추가·삭제·공통 줄 비교 | 단순 같은 줄 번호 비교만으로 삽입·삭제를 올바르게 구별하는지 검토 |
| 두 부모의 Merge | DAG·공유 조상·다중 최단 경로 | 두 HEAD를 부모로 등록하고 자식·이웃·역색인·현재 브랜치를 일관되게 갱신 |
| 정렬 두 종류 이상 성능 비교 | 평균/최악과 실제 측정의 차이 | 두 알고리즘의 정확성부터 확인하고 같은 입력 크기·분포·조건에서 측정 |

학습 목표와 연결하면 Merge를 먼저 설계해 보는 것이 유용합니다. 모델의 복수 부모 지원을 실제 명령으로 연결하고, 지금은 알고리즘 입력으로만 확인하는 공유 조상 사례를 CLI에서도 관찰할 수 있기 때문입니다. 별도의 실습용 확장이며 필수 구현에 추가한 것은 아닙니다.

영속 저장·캐시·인덱스 분산은 더 나아갈 학습 주제이지만 원문에 제시된 세 보너스와는 구분해야 합니다. 먼저 필수 명령과 경계 사례를 설명·재현할 수 있는지 확인한 뒤 확장을 선택하세요.
