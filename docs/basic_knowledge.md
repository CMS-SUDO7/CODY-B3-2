# Mini Git 기초 문법과 핵심 자료구조  

코드를 외우기보다 **왜 이 자료구조와 알고리즘을 사용하는지** 설명하는 것이 목표입니다. 이 문서는 이번 배포 코드(main.py, repository.py, algorithms.py)를 기준으로 통합했습니다. 실행은 [README.md](../README.md), 줄별 해설은 [code_translation.md](code_translation.md)를 참고하세요.  

## 1. 이 미션은 무엇을 배우게 하는가?  

버전 기록을 관리하려면 기록을 저장하고, 기록 사이의 관계를 표현하고,  
원하는 기록을 검색하고, 특정 순서로 출력해야 합니다.  
이 문제들을 하나의 프로그램으로 연결하는 연습입니다.  

| 기능 | 배우는 개념 | 설명할 수 있어야 하는 질문 |  
| --- | --- | --- |
| 커밋 저장 | 데이터 모델, 해시맵 | 필요한 필드는 무엇이며 hash로 어떻게 찾는가? |  
| 브랜치 | 참조, 상태 | 기존 커밋을 복사하지 않고 작업을 나눌 수 있는 이유는? |  
| 커밋 관계 | 그래프, DAG | 부모가 여러 명일 수 있고 순환은 없어야 하는 이유는? |  
| 기본 LOG | 위상 정렬 | 부모가 먼저 나와야 하는 조건을 어떻게 지키는가? |  
| PATH | BFS | 연결 수가 가장 적은 경로를 어떻게 찾는가? |  
| ANCESTORS | DFS, 방문 집합 | 모든 조상을 중복 없이 찾으려면? |  
| 옵션 LOG | 비교 정렬, 안정성 | 같은 값의 순서와 평균/최악 성능은? |  
| SEARCH | 역색인 | 저장 때 무엇을 미리 해두면 검색이 빨라지는가? |  
| REPL | 입력 해석, 예외, 책임 분리 | 잘못된 입력 이후에도 상태를 지키려면? |  

### 먼저 이해할 세 가지  

1. **브랜치는 커밋 복사본이 아니라 커밋 hash를 가리키는 이름**입니다.  
2. **커밋은 부모를 향한 간선으로 연결된 DAG**이며, LOG/PATH/ANCESTORS는 같은  
   그래프를 서로 다른 규칙으로 탐색합니다.  
3. **역색인은 검색 때 전체 메시지를 다시 읽지 않도록 저장할 때 만든 반대 방향 표**입니다.  

## 2. 먼저 알아야 할 기초  

### 값, 변수, list, dict, set, None  

변수는 값에 붙인 이름입니다. `message = "Add login"`은 문자열에 message라는 이름을 붙입니다.  

| 문법 | 작은 예 | 이 미션에서 필요한 이유 |  
| --- | --- | --- |
| 문자열 str | `"Add login"` | 메시지, 작성자, 식별자 표현 |  
| 목록 list | `["a", "b"]` | 부모와 탐색 대기열의 순서 보존 |  
| 사전 dict | `{"main": "a"}` | 브랜치 이름으로 마지막 커밋 찾기 |  
| 집합 set | `{"a", "b"}` | 조상의 중복 방문 제거, 검색 교집합 |  
| None | `{"main": None}` | 아직 커밋이 없는 상태. 문자열 "None"과 다름 |  

`repo.commits[commit_id]`는 사전에서 커밋 정보를 가져옵니다. `parents[0]`은 목록의 첫 원소입니다. Python의 위치는 0부터 시작합니다. 사전의 키 접근과 목록의 위치 접근을 구분하세요.  

### 처음 보면 낯선 문법  

| 코드 | 의미와 사용 위치 |  
| --- | --- |
| `items[:middle]` | 앞 절반의 새 목록. merge_sort에서 분할 |  
| `path[::-1]` | 목록을 역순으로 복사. shortest_path에서 복원 |  
| `lambda cid: ...` | 입력 하나로 비교값을 꺼내는 짧은 함수. Repository.log |  
| `mapping.get(key, [])` | 키가 없으면 빈 목록. 검색 결과 없음 처리 |  
| `mapping.setdefault(key, [])` | 키가 없으면 빈 목록을 실제 사전에 만들고 반환. 색인 갱신 |  
| `dict.fromkeys(parents)` | 같은 부모를 한 번씩만 남기며 입력 순서 유지 |  
| `f'{number:016x}'` | 정수를 16진수로 표시하고 왼쪽을 0으로 채워 최소 16자리로 표현 |  
| `[cid for cid in first if cid in candidates]` | first만 순회하며 후보 집합에 있는 식별자만 모으는 목록 내포 |  

마지막 줄은 다음처럼 풀어 쓸 수 있습니다.  

```python
result = []  
for cid in first:  
    if cid in candidates:  
        result.append(cid)  
return result  
```

## 3. 미션에서 사용하는 용어  

| 용어 | 쉬운 정의 | 코드와의 연결 |  
| --- | --- | --- |
| CLI | Command Line Interface, 글자로 명령하는 화면 | main.py |  
| REPL | Read–Evaluate–Print Loop, 입력·실행·출력의 반복 | main.main |  
| 저장소 | 커밋과 브랜치를 모은 작업 공간 | Repository 객체 |  
| 커밋 | 한 시점의 변경 설명과 작성자·시각·부모를 묶은 기록 | commits의 값 사전 |  
| 메타데이터 | 내용 자체를 설명하는 정보 | message, author, timestamp, parents |  
| 브랜치 | 특정 마지막 커밋을 가리키는 이름 | branches 사전 |  
| HEAD | 현재 작업 위치 | current_branch와 head() |  
| 노드 / 간선 | 대상 하나 / 대상 사이 연결 | 커밋 / 부모 관계 |  
| DAG | Directed Acyclic Graph, 방향을 따라 돌아와 순환할 수 없는 그래프 | 커밋에서 기존 부모로의 연결 |  
| 해시맵 | 키로 값을 찾는 자료구조 | Python dict |  
| 역색인 | 단어에서 그 단어가 있는 기록으로 가는 찾아보기 | keyword_index, author_index |  
| 위상 정렬 | 선행 조건을 만족한 대상부터 나열하는 순서 | 부모를 먼저 출력하는 LOG |  
| BFS | Breadth-First Search, 가까운 거리부터 넓게 탐색 | PATH |  
| DFS | Depth-First Search, 한 방향을 깊게 따라 탐색 | ANCESTORS |  
| 안정 정렬 | 비교값이 같은 항목들의 원래 순서 보존 | merge_sort의 <= |  
| UTC | Coordinated Universal Time, 세계 협정시 | timestamp의 +00:00 |  

한국 시간은 UTC보다 9시간 빠릅니다. 로그 시각은 일관된 비교를 위해 모두 UTC로 기록합니다.  

## 4. Git, GitHub, 이 프로그램의 범위  

- **Git**: 변경 이력과 버전을 관리하는 분산 버전 관리 시스템입니다.  
- **GitHub**: Git 저장소를 온라인에서 보관하고 협업할 수 있게 하는 서비스입니다.  
- **Mini Git**: 이 미션에서는 커밋의 메타데이터와 관계를 메모리에 관리하는 학습 프로그램입니다.  

분산 버전 관리는 각 개발자의 로컬 저장소도 이력을 보유할 수 있다는 뜻입니다.  
이 프로그램에는 원격 저장소나 동기화가 없으므로 분산 통신 자체를 구현한 것은 아닙니다.  

실제 Git은 파일 상태를 나타내는 객체들도 관리하지만, 이 과제의 `COMMIT "수정"`은  
실제 작업 파일을 저장하지 않습니다. 메시지, 사용자, 시각, 부모 관계를 기록합니다.  

## 5. 커밋은 어떤 데이터인가?  

커밋 하나를 다음 필드로 표현합니다.  

| 필드 | 예 | 의미 |  
| --- | --- | --- |
| `hash` | `0000000000000003` | 커밋을 구분하는 식별자 |  
| `message` | `Add login feature` | 무엇을 기록했는지 설명 |  
| `author` | `Kim Min Su` | 작성자 |  
| `timestamp` | UTC 시간대가 포함된 시각 | 생성 시각 |  
| `parents` | `["0000000000000001"]` | 바로 이전 커밋들의 식별자 |  

이 구현은 별도 dataclass 대신 Python **dict(사전)** 하나로 커밋을 표현합니다. `parents`는 리스트입니다. `Repository.add_commit`이 다섯 필드를 한 번에 저장합니다. 기존 커밋의 부모를 수정하는 CLI는 없지만, frozen 객체처럼 Python 차원에서 변경을 막은 구조는 아닙니다.  

`parents`가 빈 리스트이면 이전 커밋이 없는 **루트 커밋**입니다.  
부모가 하나면 일반적인 이어지는 기록, 여러 개면 여러 흐름이 연결된 기록을 표현할 수 있습니다.  

## 6. 커밋, 브랜치, HEAD를 구분하기  

**브랜치는 특정 커밋을 가리키는 이름입니다. HEAD는 현재 작업 위치를 나타냅니다.**  
현재 브랜치 이름은 current_branch에 저장하고, head()가 그 브랜치의 마지막 커밋 식별자를 반환합니다.  

```python
branches = {"main": "0000000000000002", "feature": "0000000000000004"}  
current_branch = "feature"  
current_commit_hash = branches[current_branch]  # "0000000000000004"  
```

실제 Git에는 브랜치에서 떨어진 detached HEAD 상태도 있지만 이 미션에서는 다루지 않습니다.  

아래 동작을 종이에 직접 따라 그릴 수 있어야 합니다.  

| 명령 | 생성/변경되는 내용 | HEAD |  
| --- | --- | --- |
| `INIT learner` | main → 없음 | main |  
| `COMMIT "A"` | 커밋 1 생성, main → 1 | main |  
| `BRANCH feature` | feature → 1이라는 이름 추가 | main |  
| `SWITCH feature` | 현재 브랜치만 변경 | feature |  
| `COMMIT "B"` | 부모가 1인 커밋 2 생성, feature → 2 | feature |  
| `SWITCH main` | main이 가리키는 커밋 1에서 작업 | main |  
| `COMMIT "C"` | 부모가 1인 커밋 3 생성, main → 3 | main |  

브랜치를 만들 때 커밋 1을 복사하지 않습니다. 두 이름이 같은 식별자를 가리킵니다.  
따라서 브랜치 생성/전환은 평균 O(1)입니다.  

**코드 연결:** `Repository.branches`, `Repository.current_branch`, `Repository.head()`, `branch`, `switch`, `commit`.  

## 7. 그래프, 트리, DAG  

- **노드(vertex)**: 커밋 하나.  
- **간선(edge)**: 두 커밋 사이의 부모 연결.  
- **방향 그래프**: 간선에 방향이 있는 그래프.  
- **사이클(cycle)**: 간선 방향을 따라 출발한 노드로 돌아오는 순환.  
- **DAG**: Directed Acyclic Graph, 방향성 비순환 그래프.  

이 프로그램에 저장된 참조 방향은 **자식 → 부모**입니다.  
새 커밋은 자신보다 먼저 존재한 커밋만 부모로 삼습니다.  
기존 커밋의 부모를 바꾸지 않으므로, 이전 커밋이 아직 생성되지 않은 새 커밋을  
가리키는 연결은 없습니다. 이 규칙이 순환을 방지합니다.  

시각이 항상 증가해서 DAG인 것이 아닙니다. 시계가 잘못되어 날짜가 뒤로 가더라도  
부모 연결 규칙을 지키면 DAG입니다.  

부모가 여러 명인 병합 관계는 일반적인 트리로 표현하기 어렵습니다. 그래서 모델은  
부모 목록을 가진 그래프로 만듭니다. 다만 이 과제의 CLI `COMMIT`만으로 만들어지는  
구조는 부모가 최대 하나인 트리 또는 여러 트리의 모음입니다.  

**DAG라고 무방향 사이클까지 없는 것은 아닙니다.** 공통 부모에서 두 갈래로 나뉜 뒤  
여러 부모 커밋으로 합쳐지면 방향을 무시할 때 순환이 생길 수 있습니다.  
이는 PATH에서 여러 최단 경로가 생기는 이유이기도 합니다.  

**코드 연결:** `commits[식별자]['parents']`, `Repository.add_commit`의 부모 존재 검사.  

## 8. 위상 정렬: 부모가 먼저 출력되는 LOG  

위상 정렬은 **선행 관계를 어기지 않도록 노드를 나열하는 것**입니다.  
수업 선수 과목이나 작업 의존성 순서를 정할 때도 같은 문제를 만납니다.  

부모 A를 가진 B는 A가 출력된 다음 출력되어야 합니다.  
이 프로그램은 Kahn 알고리즘을 사용합니다.  

1. 각 커밋의 아직 출력하지 않은 부모 수를 `remaining`에 기록합니다.  
2. 부모 수가 0인 커밋을 큐에 넣습니다.  
3. 큐에서 커밋 하나를 꺼내 출력 목록에 추가합니다.  
4. 그 커밋의 자식들이 기다리는 부모 수를 1씩 줄입니다.  
5. 기다리는 부모가 0명이 된 자식을 큐에 넣습니다.  
6. 모든 커밋을 처리할 때까지 반복합니다.  

주의할 점은 **간선 방향을 해석하는 기준**입니다.  
저장된 참조는 자식→부모이지만, 여기서는 출력 선행 관계를 부모→자식으로 봅니다.  
`remaining`은 이 선행 관계에서의 진입 차수, 즉 기다리는 부모 수입니다.  

모든 노드와 간선을 처리하므로 시간은 O(V + E)입니다.  
자식 목록은 커밋 생성 때 저장소에 미리 유지합니다. LOG 실행 시 추가 공간은 O(V)이며, 저장된 연결 목록 공간은 별도로 O(V + E)입니다.  
처리한 커밋 수가 전체보다 작다면 순환이 존재한다고 판단합니다.  

위상 순서는 여러 개일 수 있습니다. 서로 부모·자식이 아닌 B, C는 B가 먼저여도,  
C가 먼저여도 조건을 만족할 수 있습니다. 이 프로그램은 큐와 생성 순서로 결과를 고정합니다.  

**날짜 정렬과의 차이:** 날짜는 값이고 부모 관계는 의존성입니다. 부모 시각이 자식보다  
늦게 기록되었다면 날짜순과 부모 우선 순서가 달라질 수 있습니다.  

**코드 연결:** `topological_order`, `Repository.log`.  

## 9. BFS: 간선 수가 최소인 경로  

BFS는 Breadth-First Search, **너비 우선 탐색**입니다.  
현재 노드에서 1번 이동한 곳, 2번 이동한 곳, 3번 이동한 곳을 차례로 확인합니다.  

각 간선을 이동하는 비용이 모두 1이면, BFS가 처음 발견한 거리가 최단 거리입니다.  
거리마다 비용이 다르면 일반적인 BFS만으로 최소 비용을 보장할 수 없습니다.  

이 미션의 PATH는 부모 연결을 무방향으로 취급하므로 부모뿐 아니라 자식으로도 이동합니다.  
이를 위해 기존 부모 필드를 바꾸는 대신 PATH 전용 양방향 인접 목록을 만듭니다.  

### 사전순 동률까지 처리하는 방법  

최단 경로가 아래 두 개라고 가정합니다.  

- `0000000000000001->0000000000000002->0000000000000004`  
- `0000000000000001->0000000000000003->0000000000000004`  

간선 수는 모두 2개지만 첫 번째 경로 문자열이 사전순으로 앞섭니다.  

현재 코드는 **출발점에서 BFS**를 수행합니다. 각 노드의 이웃을 직접 구현한 병합 정렬로 사전순 방문하고, 처음 방문할 때의 이전 노드를 `previous`에 기록합니다.  

| 단계 | queue | previous | 의미 |  
| --- | --- | --- | --- |
| 시작 | [1] | {1: None} | 출발점 등록 |  
| 1 처리 | [1, 2, 3] | {1: None, 2: 1, 3: 1} | 같은 거리에서는 작은 식별자 먼저 |  
| 2 처리 | [1, 2, 3, 4] | 위 내용에 4: 2 추가 | 목적지의 최초 경로 확보 |  
| 3 처리 | 그대로 | 그대로 | 이미 방문 등록한 4는 덮어쓰지 않음 |  
| 4 처리 | 그대로 | 그대로 | 4, 2, 1을 역추적해 1, 2, 4 반환 |  

표의 숫자는 16자리 식별자의 축약입니다. BFS는 거리 순으로, 같은 거리에서는 경로 앞부분이 작은 후보부터 확장합니다. 처음 도달한 경로가 사전순 최소 최단 경로가 됩니다. 식별자는 같은 길이의 16진 문자열이라 `->`로 연결한 문자열 비교와도 일치합니다.  

예전 자료의 **목적지부터 거리 계산 → 거리가 1 줄어드는 이웃 중 최소 선택**도 올바른 대안입니다. 두 방법을 동시에 실행하는 것이 아닙니다. 현재 코드는 출발점 BFS이며 실제 기능 검증에서도 완전탐색 정답과 비교했습니다.  

BFS 자체는 O(V+E)이지만 현재 코드는 이웃을 정렬하므로 **O(V+E+Σ d(u)log d(u))** 상한입니다. d(u)는 탐색 중 처리한 노드 u의 이웃 수입니다. 이전 방식보다 고차수 그래프에서 추가 정렬 비용이 있습니다. 기능을 생략한 것은 아니며, 이 차이를 복잡도 설명에서도 구분해야 합니다.  

**코드 연결:** `shortest_path`의 `neighbors`, `previous`, `queue`, `front`.  

## 10. DFS와 visited: 모든 조상 찾기  

DFS는 Depth-First Search, **깊이 우선 탐색**입니다.  
한 연결을 따라 깊이 들어간 뒤 남은 연결로 돌아옵니다.  

ANCESTORS는 부모 방향만 탐색합니다. 부모, 부모의 부모를 계속 확인하면 모든 조상을  
찾을 수 있습니다. DFS 대신 BFS를 사용해도 모든 조상을 찾는 목적은 달성할 수 있습니다.  

여러 부모가 같은 조상을 공유하면 동일 노드에 여러 경로로 도달합니다.  
`visited`에 이미 확인한 hash를 기록해 중복 출력과 불필요한 재탐색을 막습니다.  
시작 커밋의 부모부터 스택에 넣으므로 정상 DAG에서 자기 자신은 결과에 들어가지 않습니다.  

이 구현은 재귀 호출 대신 리스트 스택을 사용합니다. 따라서 커밋 이력이 깊어져도  
DFS의 재귀 호출 제한에 걸리지 않습니다.  

### 스택과 큐의 차이  

| 자료구조 | 꺼내는 순서 | 사용 위치 |  
| --- | --- | --- |
| 스택 | 나중에 넣은 것을 먼저 꺼냄, LIFO | DFS의 `append`, `pop` |  
| 큐 | 먼저 넣은 것을 먼저 꺼냄, FIFO | BFS, Kahn의 리스트와 읽기 커서 |  

리스트의 `pop(0)`은 뒤 원소를 앞으로 이동시켜 O(N)이 걸립니다.  
그래서 큐는 삭제하지 않고 `front`를 증가시키며 읽습니다. 각 읽기는 O(1)입니다.  
읽은 원소가 끝날 때까지 리스트에 남으므로 공간은 방문 노드 수에 비례합니다.  

**코드 연결:** `ancestor_ids`.  

## 11. 직접 구현한 병합 정렬  

병합 정렬은 **나누기 → 각각 정렬하기 → 정렬된 두 목록 합치기**를 반복합니다.  
합칠 때는 두 목록의 맨 앞 원소를 비교해 더 작은 것을 결과에 넣습니다.  

매 단계 전체 원소를 합치는 데 O(N), 반으로 나누는 깊이가 O(log N)이므로  
평균/최악 시간복잡도가 모두 O(N log N)입니다. 이 구현은 새 목록을 사용해 추가 공간 O(N),  
재귀 깊이 O(log N)이 필요합니다. 평균과 최악을 모두 알아야 하는 이유는 입력 모양에  
따라 급격하게 느려지는 알고리즘도 있기 때문입니다.  

| 정렬 | 평균 | 최악 | 안정성 |  
| --- | --- | --- | --- |
| 이 구현의 병합 정렬 | O(N log N) | O(N log N) | 안정 |  
| 일반적인 제자리 퀵 정렬 | O(N log N) | O(N²) | 보통 불안정 |  
| 일반적인 삽입 정렬 | O(N²) | O(N²) | 같은 값을 넘기지 않으면 안정 |  

### 안정 정렬이란?  

정렬 기준값이 같은 원소끼리 기존 상대 순서를 유지하는 것입니다.  

| 생성 순서 | 작성자 |  
| --- | --- |
| A | Kim |  
| B | Lee |  
| C | Kim |  

작성자로 안정 정렬하면 A, C, B가 됩니다. 같은 Kim인 A와 C의 원래 순서는 유지됩니다.  
코드에서 `key(left[i]) <= key(right[j])`로 비교하여 같을 때 왼쪽을 먼저 선택합니다.  

### 비교 기준을 바꾼다는 뜻  

정렬 알고리즘 자체를 두 개 만들지 않고, 비교에 사용할 값만 전달합니다.  

```python
merge_sort(list(repo.commits), key=lambda cid: repo.commits[cid]["timestamp"])  
merge_sort(list(repo.commits), key=lambda cid: repo.commits[cid]["author"])  
```

`lambda`는 짧은 함수 표현입니다. 첫 줄은 각 커밋의 시각을, 둘째 줄은 작성자를  
비교값으로 꺼냅니다. 시간·작성자가 같으면 원래 커밋 생성 순서를 유지합니다.  

정렬 기준을 바꾼 LOG는 부모 우선 조건을 별도로 적용하지 않습니다.  
**코드 연결:** `merge_sort`, `Repository.log`.  

## 12. 역색인: 검색할 때 할 일을 저장할 때 해두기  

일반적인 커밋 저장소는 `hash → 커밋`입니다.  
메시지로 찾으려면 반대 방향의 연결인 `단어 → 해당 커밋 hash들`을 미리 만듭니다.  
이것을 역색인이라고 합니다.  

| 커밋 | 메시지 |  
| --- | --- |
| A | Add login |  
| B | Fix login bug |  
| C | Add logout |  

| 토큰 | 연결된 커밋 |  
| --- | --- |
| add | A, C |  
| login | A, B |  
| fix | B |  
| bug | B |  
| logout | C |  

`SEARCH login`은 login 항목에서 A, B를 찾습니다. C의 메시지를 검사하지 않습니다.  
`SEARCH "add login"`은 두 목록에 모두 있는 A를 찾습니다.  
현재 코드는 첫 단어의 색인 목록으로 후보 집합을 만들고, 나머지 단어의 목록과 교집합을 계산합니다. 마지막에는 첫 목록 순서로 결과를 모아 생성 순서를 유지합니다. 가장 작은 목록부터 고르는 최적화는 적용하지 않았습니다.  

키워드와 작성자 색인은 모두 `dict[str, list[str]]`, 즉 문자열 키에서 식별자 목록을 찾는 사전입니다. 키워드 중복은 저장 시 `set(message.lower().split())`으로 제거합니다. 검색 시 교집합에 set을 사용하며 전체 커밋 메시지를 순회하지 않습니다.  

### 토큰화 정책을 이해하기  

| 원래 문자열 | 정규화된 토큰 |  
| --- | --- |
| `Add LOGIN` | add, login |  
| `login login` | login 한 개 |  
| `login,` | login, (쉼표 포함) |  
| `login_feature` | login_feature 한 개 |  

`SEARCH log`로 `login`을 찾을 수는 없습니다. 부분 문자열 검색과 정확 토큰 검색은  
다른 기능입니다. 공백을 포함한 검색어는 각 단어를 모두 포함한다는 AND 조건이며,  
단어가 연속하는지를 확인하는 문구 검색은 아닙니다.  

### 왜 빠르고, 어떤 비용을 치르는가?  

전체 순회 검색은 각 메시지를 읽기 때문에 전체 텍스트 길이에 비례하는 일이 생깁니다.  
단일 토큰 역색인 검색은 조회 평균 O(1)에 결과 K개를 가져오는 O(K)가 필요합니다.  
검색어 문자열 정규화와 결과 문자열 출력에는 별도 비용이 있습니다.  

대신 커밋 생성 때 토큰을 추출하고 인덱스를 갱신해야 하며, 토큰-커밋 연결을 저장할  
메모리가 필요합니다. 많은 커밋이 같은 단어를 포함하면 K가 전체 커밋 수만큼 커질 수  
있습니다. 검색 결과가 많을 때도 언제나 상수 시간이라는 뜻은 아닙니다.  

**코드 연결:** `Repository.keyword_index`, `Repository.add_commit`, `Repository.search`.  

## 13. 복잡도를 설명하는 법  

O 표기는 입력이 커질 때의 작업량 증가를 나타내며 실제 초 단위 시간이 아닙니다. 같은 노드 수라도 연결 수가 다르면 그래프 탐색 비용이 달라집니다. dict 조회의 평균 O(1)과 결과 K개를 출력하는 O(K)도 구분해야 합니다.  


V는 커밋 수, E는 부모 연결 수, R은 방문한 노드 수, E_R은 방문 영역에서 확인하는 연결 수입니다. L은 메시지 길이, K는 일치 커밋 수, P_i는 i번째 검색 단어 색인 목록 길이입니다. 평균 dict/set 조회 O(1), list append 분할상환 O(1), 문자열 비교를 상수 시간으로 보는 단순 모델 기준입니다. 긴 작성자·검색 문자열은 처리 길이만큼 추가 비용이 듭니다.  

| 작업 | 시간 | 추가 공간 | 전제와 범위 |  
| --- | --- | --- | --- |
| 브랜치 생성·전환, HEAD 조회 | 평균 O(1), 해시 충돌 최악 O(B) | 생성 O(1) | B는 브랜치 수, 문자열 키 길이 제외 |  
| 일반 COMMIT | 평균/분할상환 O(L+1) | O(L+1) 규모 신규 정보 | 부모 최대 1개. 다중 부모 p개는 O(L+p) |  
| LOG 위상 정렬 | O(V+E) | O(V) | 해시 접근 평균 전제, 화면의 문자 출력 비용 제외 |  
| ANCESTORS | O(R+E_R) | O(R+E_R) | 중복 후보가 스택에 들어갈 수 있어 스택 공간을 단순 O(R)로 단정하지 않음 |  
| PATH | O(R+E_R+Σ d(u)log d(u)) | O(R+Δ) | 방문 이웃 정렬 비용 포함. Δ는 최대 차수 |  
| 병합 정렬 | 평균·최악 O(V log V), 빈 입력 O(1) | 최대 동시 O(V), 호출 깊이 O(log V) | 비교값 추출·비교가 O(1)인 모델 |  
| 단어 1개 / 작성자 검색 | 평균 O(Q+K) | O(K) | Q는 질의 문자열 길이. 결과 복사·출력 포함 시 K를 생략할 수 없음 |  
| 여러 단어 AND 검색 | 평균 O(Q+Σ P_i) | O(P_1 + max P_i + Q) 상한 | 관련 색인만 순회. 집합 교집합의 임시 저장 포함 |  

그래프·색인 전체 저장 공간은 메시지 본문 및 이름 크기를 별도로 세면 O(V+E+T+B)입니다. T는 중복 제거 후 단어-커밋 연결의 총수입니다. E가 커지면 인접 목록에도 그만큼 저장 공간이 필요합니다.  

병합 정렬은 비교 시 매번 전체 정렬을 다시 하지 않습니다. 분할 깊이 약 log₂V 단계마다 총 V개 정도를 병합하므로 O(V log V)입니다. 이 코드의 슬라이싱도 각 단계에서 복사 비용이 들지만 같은 점근적 시간 범위 안에 있습니다. 선택 정렬은 보통 O(V²)여서 큰 로그에는 불리하고, 퀵 정렬은 구현에 따라 최악 O(V²)와 불안정성이 있어 안정적인 병합 정렬을 골랐습니다.  

## 14. REPL, 파싱, 오류 처리, 불변 조건  

REPL은 Read-Evaluate-Print Loop입니다. 입력을 읽고, 명령을 실행하고,  
결과를 출력한 뒤 다음 입력을 받습니다.  

`COMMIT "Add login feature"`를 단순 `split()`으로 나누면 따옴표 안의 공백까지  
분리됩니다. `shlex.split()`은 인용 문자열을 한 인자로 해석합니다.  
명령 이름만 대문자로 바꾸고 메시지의 원문은 그대로 저장합니다.  

### 역할 분리  

| 구성 요소 | 책임 |  
| --- | --- |
| 커밋 dict | 다섯 필드를 가진 기록 한 개 표현 |  
| 탐색/정렬 함수 | 알고리즘 실행 |  
| keyword_index / author_index | Repository 안에서 검색용 연결 관리 |  
| `Repository` | 커밋/브랜치/사용자 상태 관리 |  
| `validate` / `execute` | 문법 검사 / 메서드 호출과 출력 구성 |  
| `main` | 반복 입력과 오류 메시지 출력 |  

**불변 조건(invariant)**은 정상 동작 중 항상 지켜야 하는 규칙입니다.  

- HEAD는 존재하는 브랜치를 가리킵니다.  
- 브랜치 끝은 None 또는 존재하는 커밋 hash입니다.  
- 커밋 부모는 존재하며, 기존 커밋 부모 관계를 수정하지 않습니다.  
- 모든 커밋 hash가 유일합니다.  
- 커밋을 추가하면 작성자/키워드 인덱스에도 반영합니다.  
- 잘못된 사용자 입력은 커밋과 브랜치를 부분 변경하지 않습니다.  

예를 들어 SWITCH는 브랜치가 존재하는지 먼저 확인하고 HEAD를 바꿉니다.  
COMMIT은 validate에서 빈 메시지를 거부합니다. add_commit은 부모 중복을 제거하고 부모 존재 여부를 확인한 뒤 상태를 바꿉니다.  
예상 가능한 사용자 오류는 `ValueError`로 전달하고 REPL에서 메시지만 출력합니다.  
이것은 디스크 트랜잭션이나 메모리 부족 같은 시스템 장애까지 복구한다는 의미는 아닙니다.  

## 15. 실제 Git 명령을 이해하는 데 연결하기  

이 프로그램에 아래 명령은 없지만, 부모와 식별자 관계를 알면 원리를 이해하기 쉽습니다.  

- **merge**: 분기된 이력을 합칩니다. 새 병합 커밋이 만들어지는 경우 부모가 여러 개일  
  수 있습니다. fast-forward처럼 새 병합 커밋 없이 브랜치 참조가 이동하는 경우도 있습니다.  
- **rebase**: 커밋의 변경을 다른 기준 위에 다시 적용합니다. 재작성된 커밋은 부모 등의  
  정보가 달라지므로 새 식별자를 갖습니다.  
- **cherry-pick**: 선택한 커밋의 변경을 현재 작업 흐름에 적용해 보통 새 커밋을 만듭니다.  
  원본 커밋의 부모 관계를 그대로 옮기는 동작으로 이해하면 안 됩니다.  

Mini Git에는 실제 파일 변경 내용이 없으므로 이 명령들의 파일 병합·충돌 해결은 다루지 않습니다.  

## 16. 작은 학습 과제  

### 문제 1 — 실행 결과 예상  

새 실행에서 `INIT Alice`, `COMMIT "LOGIN login"`, `SEARCH login`, `SEARCH log`를 입력하면 각각 검색 결과는 몇 건일까요? 시작 위치는 `Repository.add_commit`의 lower/split/set과 search입니다.  

### 문제 2 — 저장 데이터 따라가기  

README의 첫 7개 명령까지 실행했다고 가정하고 branches, current_branch, 2번·3번 커밋의 parents를 적어 보세요. 시작 위치는 branch, switch, commit입니다.  

### 문제 3 — 작은 수정  

`Repository.log`에서 작성자 비교만 대소문자를 무시하도록 고쳐 보세요. 저장된 원래 작성자 이름과 작성자 검색 규칙은 유지하는 것이 목표입니다. date 정렬은 그대로 두세요.  

### 힌트와 해설  

1. login은 1건, log는 0건입니다. 중복 단어는 set으로 한 번만 색인하고 부분 문자열은 찾지 않습니다.  
2. main은 3번, feature는 2번, 현재 브랜치는 main입니다. 2번과 3번의 부모는 모두 1번입니다. SWITCH는 새 커밋을 만들지 않습니다.  
3. author 분기에서만 `lambda cid: self.commits[cid]['author'].lower()`를 key로 전달합니다. `self.user`나 색인 키를 직접 소문자로 바꾸면 검색과 원문 보존까지 달라져 목표를 벗어납니다.  

## 17. 나중에 공부할 확장 지식  

- 실제 Git은 파일 내용에서 객체 식별자를 계산하고 디스크에 저장합니다. 이 구현의 숫자 식별자·메모리 사전과 차이가 있습니다.  
- 실제 병합은 부모 두 개 기록뿐 아니라 파일 내용과 충돌 해결도 필요합니다.  
- 파일 영속성을 추가할 때 JSON 저장·읽기, 스키마 검증, 원자적 교체를 학습할 수 있습니다.  
- 많은 기록을 처리할 때 색인 압축, 정렬된 이웃 캐시, 부모 탐색 최적화를 생각해 볼 수 있습니다.  

위 항목은 현재 제출물의 필수 기능이 아닙니다.
