# B3-2 기초·핵심 지식

먼저 **① 브랜치는 커밋 복사본이 아니라 위치를 가리킨다 ② 기본 LOG는 시간순이 아니라 부모 우선이다 ③ 역색인은 단어에서 커밋으로 바로 가는 표다**라는 세 가지를 이해하세요.

## 1. 먼저 알아야 할 기초

### 함수·반환·출력

함수는 이름을 붙인 작업 묶음입니다. `Repository.path(start, target)`는 두 hash를 입력받아 경로의 hash 목록을 **반환**합니다. `main.py`는 그 목록을 문자열로 바꾸어 **출력**합니다. 반환값은 다른 코드가 사용할 수 있고 출력은 사람이 화면에서 읽습니다. 탐색 로직과 화면 표시를 나누면 CLI 문구를 바꿔도 알고리즘은 유지됩니다.

### 클래스·인스턴스·self

클래스는 관련 데이터와 동작을 묶는 설계도이며 `Repository()`는 그 설계도로 만든 객체, 즉 인스턴스입니다. 메서드의 `self`는 현재 객체입니다. `self.branches`는 해당 저장소의 브랜치 표이고, `repository.create_branch("feature")`는 그 표를 변경합니다.

`Repository.commit()`은 생성한 `Commit` 객체를 반환합니다. `Commit`은 `@dataclass(frozen=True)`를 사용하여 생성자 같은 반복 코드를 자동으로 만들고 필드 재대입을 막습니다. `hash: str`의 타입 힌트는 문자열을 기대한다는 표시이며 입력을 자동 검증하는 장치는 아닙니다.

### list·dict·set·tuple

| 자료형 | 쉬운 정의·작은 예 | 사용 위치·필요한 이유 |
| --- | --- | --- |
| list | 순서 있는 목록: `["c1", "c2"]` | 자식·이웃·검색 결과의 순서를 유지 |
| dict | 키로 값을 찾는 표: `{"main": "c2"}` | `branches`는 브랜치에서 커밋으로, `commits`는 hash에서 객체로 조회 |
| set | 중복 없는 모음: `{"login", "add"}` | 인덱싱 시 같은 단어 중복 제거, DFS 방문 여부 확인 |
| tuple | 생성 후 항목을 바꾸지 않는 순서 묶음: `("c1",)` | `Commit.parents`를 변경하기 어렵게 보관 |

`(parent,)`의 쉼표가 있어야 원소 하나의 튜플입니다. `(parent)`는 괄호로 감싼 값일 뿐입니다. 첫 커밋의 부모는 빈 튜플 `()`입니다. `None`은 빈 문자열이나 hash가 아니라 값이 없음을 나타냅니다.

`commits[hash]`는 정확한 hash로 직접 조회합니다. 대체로 빠르지만 딕셔너리가 모든 상황에서 무조건 O(1)을 보장하는 것은 아닙니다.

### 문자열·인자 파싱·예외

`"Add LOGIN".lower().split()`은 `["add", "login"]`입니다. `.split()`은 공백으로 분리하고 `.lower()`는 소문자로 통일합니다. 이 규칙을 등록과 검색에서 똑같이 써야 검색이 맞습니다. `index.py`에서 실제 사용합니다.

반면 CLI 입력은 따옴표를 이해해야 합니다. `shlex.split('COMMIT "Add login"')`은 `['COMMIT', 'Add login']`이 됩니다. 단순 `.split()`을 쓰면 메시지가 둘로 나뉩니다. `main.execute()`가 이 차이를 처리합니다.

`raise ValueError("Invalid args")`는 잘못된 입력을 알리고, `main()`의 `except ValueError`는 화면에 오류를 보여준 후 다음 입력을 받습니다. 오류 때문에 잘못된 커밋이 생성되지 않도록 인자 검증을 먼저 합니다.

## 2. 미션에서 사용하는 용어

| 용어 | 의미 | 코드 연결 |
| --- | --- | --- |
| CLI, Command Line Interface | 텍스트 명령으로 조작하는 화면 | `main.py` |
| REPL, Read–Eval–Print Loop | 읽기·실행·출력을 반복하는 방식 | `main()`의 반복문 |
| 저장소, repository | 커밋과 브랜치를 관리하는 묶음 | `Repository` |
| 커밋, commit | 작성자·메시지·시각·부모를 가진 기록 | `Commit` |
| hash | 커밋을 구별하는 식별자. 여기서는 증가 정수의 16진수 표현 | `Repository.commit()` |
| 부모, parent | 새 커밋의 바탕이 된 기존 커밋 | `Commit.parents` |
| 브랜치, branch | 특정 커밋을 가리키는 이름 | `branches` |
| HEAD | 현재 작업 위치. 여기서는 현재 브랜치를 통해 커밋을 찾음 | `current_branch`와 `branches` |
| 노드·간선 | 그래프의 점과 점 사이 연결 | 커밋과 부모 관계 |
| DAG, Directed Acyclic Graph | 방향이 있으며 그 방향을 따라 되돌아오는 순환이 없는 그래프 | 커밋 → 부모 |
| 인접 리스트 | 각 노드에 직접 연결된 노드의 목록 | `children`, `neighbors` |
| 위상 정렬 | 선행 관계를 위반하지 않는 노드 순서 | `topological_order()` |
| 역색인, inverted index | 단어/작성자에서 해당 커밋 목록으로 가는 표 | `InvertedIndex` |
| 안정 정렬 | 기준 값이 같을 때 입력의 상대 순서를 유지하는 정렬 | `merge_sort()` |

이 구현의 hash는 암호학적 해시 함수로 내용을 요약한 값이 아닙니다. 원문에서 허용한 증가 카운터 방식이며 실제 Git의 내용 기반 객체 식별과 구분해야 합니다.

## 3. 이번 미션의 핵심

### 3-1. 브랜치를 만들면 커밋을 복사할까?

다음 상태를 생각해 보세요.

| 작업 | main | feature | 현재 브랜치 |
| --- | --- | --- | --- |
| INIT Alice | None | 없음 | main |
| COMMIT root | 00000001 | 없음 | main |
| BRANCH feature | 00000001 | 00000001 | main |
| SWITCH feature | 00000001 | 00000001 | feature |
| COMMIT login | 00000001 | 00000002 | feature |

`create_branch()`는 현재 hash를 새 이름에 연결합니다. 커밋 객체는 복사하지 않습니다. 이후 `commit()`은 현재 브랜치의 참조만 새 hash로 바꿉니다. 이 구조 덕분에 과거 커밋을 공유하고 각 브랜치가 서로 다른 방향으로 발전할 수 있습니다.

### 3-2. 왜 DAG인가?

`Repository.commit()`은 **이미 존재하는 HEAD를 부모**로 삼는 새 노드만 추가합니다. 기존 커밋의 부모는 수정하지 않습니다. 새 노드에서 부모로 계속 가면 생성 시점이 더 이른 노드만 만나므로 자기 자신으로 돌아올 수 없습니다. 부모 튜플과 frozen 데이터 모델이 이 규칙을 유지하도록 돕습니다. frozen만으로 임의 그래프의 DAG가 자동 보장되는 것은 아닙니다.

필수 CLI에서 부모는 최대 한 개이므로 실제 생성 그래프는 트리 또는 여러 트리의 모음에 가깝습니다. 트리는 DAG의 한 종류입니다. 모델과 탐색은 복수 부모도 받을 수 있지만 merge 명령은 선택 과제로 남겼습니다.

### 3-3. LOG와 위상 정렬

최신순으로만 출력하면 자식이 부모보다 먼저 나올 수 있습니다. 기본 LOG는 부모가 먼저라는 의존 관계를 따라야 하므로 **Kahn 알고리즘**을 사용합니다.

1. 각 커밋의 아직 출력하지 않은 부모 수를 셉니다.
2. 부모 수가 0인 커밋을 큐에 넣습니다.
3. 큐 앞에서 하나를 꺼내 결과에 추가합니다.
4. 그 커밋의 각 자식에게 남은 부모 수를 1 줄입니다.
5. 남은 부모가 0이 된 자식을 큐 뒤에 넣습니다.

`topological_order()`의 `remaining`, `ready`, `ordered`가 이 역할을 맡습니다. 원본 데이터의 `parents`는 자식→부모이고, 위상 정렬에서 사용하는 `children`은 부모→자식 방향의 보조 표입니다. 따라서 remaining은 부모→자식 표현에서의 진입 차수에 해당합니다.

`LOG --sort-by=author`는 위상 정렬 대신 이름 정렬을 요청한 별도 모드입니다. 작성자 기준 순서가 의존 관계를 거스를 수 있어 두 규칙을 동시에 강제하지 않습니다.

### 3-4. PATH는 BFS로 거리를 구한다

BFS(Breadth-First Search, 너비 우선 탐색)는 가까운 노드부터 방문합니다. 가중치 없는 간선에서 처음 기록한 거리가 최소 간선 수입니다. 이 미션은 부모 간선을 **양방향**으로 취급하므로 `neighbors`에 부모와 자식을 함께 저장합니다.

예를 들어 `feature 커밋 → root → main 커밋`은 부모로 갔다가 다른 자식으로 내려오는 2간선 경로입니다. 부모 방향만 탐색하면 이 경로를 놓칩니다.

`shortest_path()`는 목적지에서 BFS를 하여 `distance[hash]`에 목적지까지 거리를 기록합니다. 그런 다음 출발지에서 **거리가 정확히 1 줄어드는 이웃만** 선택합니다. 이 조건 때문에 최단 경로를 유지하고 순환에 빠지지 않습니다. 선택할 이웃이 여러 개면 `hash + "->"`가 가장 작은 것을 고릅니다.

#### 최단 거리 동률 예

알고리즘 함수의 입력으로 다음 연결을 생각합니다. 필수 COMMIT만으로는 다이아몬드형 다중 경로를 만들지 않으므로 CLI 재현 예가 아닙니다.

| 노드 | 양방향 이웃 |
| --- | --- |
| s | b, a |
| a | s, t |
| b | s, t |
| t | a, b |

두 경로 `s->a->t`, `s->b->t`는 모두 2간선입니다. 두 번째 hash를 처음 비교하면 a가 작으므로 전자를 선택합니다. 공통 접두 경로 이후 처음 달라지는 hash가 전체 문자열의 순서를 결정합니다.

hash 길이가 다르거나 접두 관계라면 구분자도 비교해야 합니다. 예를 들어 `a->`는 `a0->`보다 작습니다. 실제 함수는 구분자를 붙여 비교하고, 모든 최단 경로를 목록으로 만들지 않아 메모리를 절약합니다.

### 3-5. ANCESTORS는 DFS로 빠짐없이 방문한다

DFS(Depth-First Search, 깊이 우선 탐색)는 한 방향을 깊게 따라가는 탐색입니다. `find_ancestors()`는 재귀 대신 스택을 사용합니다.

- 시작 커밋 자체가 아니라 그 부모들을 스택에 넣습니다.
- 꺼낸 hash를 이미 방문했다면 건너뜁니다.
- 처음 본 hash는 결과와 방문 집합에 추가하고 그 부모들을 스택에 넣습니다.

복수 부모가 같은 조상을 공유해도 `visited`가 중복 출력을 막습니다. 2,000개처럼 긴 커밋 체인에서도 파이썬 재귀 깊이에 의존하지 않습니다.

### 3-6. 역색인은 무엇을 뒤집는가?

보통 저장소는 `커밋 → 메시지`입니다. 역색인은 `메시지 단어 → 커밋 hash 목록`을 추가로 저장합니다.

```python
keywords = {
    "add": ["00000002", "00000003"],
    "login": ["00000002"],
    "payment": ["00000003"],
}
```

`SEARCH login`은 모든 메시지를 읽는 대신 `keywords["login"]`의 후보만 조회합니다. `add()`는 메시지를 소문자로 바꾼 뒤 공백으로 나누고 set으로 같은 단어를 제거합니다. 작성자는 `authors["Alice Kim"]`처럼 전체 이름을 키로 씁니다.

여러 단어 검색은 각 후보 목록의 교집합입니다. `search_keyword()`는 가장 짧은 목록을 기준으로 삼고 각 단어의 후보 집합에 모두 들어 있는 hash만 남깁니다. 최종적으로 `Repository.search()`가 그 hash들에 대해서만 커밋 객체를 직접 찾습니다.

정확한 토큰 검색은 부분 문자열 검색과 다릅니다. `login`은 `logging`을 찾지 않으며 구두점도 보존합니다. 검색이 빨라지는 대신 커밋을 생성할 때 등록 작업과 추가 저장 공간이 필요합니다.

### 3-7. 직접 구현한 안정 병합 정렬

`merge_sort(items, key)`는 배열을 절반으로 나누고 각각 정렬한 뒤 두 배열의 앞부분을 비교해 합칩니다. `key`는 객체에서 비교할 값을 뽑는 함수입니다.

```python
key = lambda node: node.author
```

위 표현은 호출 시 커밋의 작성자를 돌려주는 작은 함수입니다. `getattr(node, field)`를 사용하면 field가 `timestamp`인지 `author`인지에 따라 기준을 바꿀 수 있습니다.

합칠 때 `<`가 아니라 **`<=`**를 사용하므로 값이 같으면 왼쪽에 있던 항목을 먼저 고릅니다. 왼쪽은 원래 입력에서 앞에 있던 부분이므로 같은 작성자·같은 시각의 커밋도 생성 순서를 유지합니다.

| 방법 | 평균/최악 비교 횟수 | 안정성·선택 이유 |
| --- | --- | --- |
| 병합 정렬 | O(N log N) / O(N log N) | 이 구현은 안정적. 시간 예측이 쉽지만 추가 배열 필요 |
| 삽입 정렬 | 일반 무작위 입력 평균 O(N²), 최악 O(N²) | 안정적으로 구현 가능. 작은 입력·거의 정렬된 입력에 적합 |
| 퀵 정렬 | 피벗이 고르게 분할될 때 평균 O(N log N), 최악 O(N²) | 일반적인 제자리 구현은 불안정. 피벗 선택의 영향이 있음 |

여기서 N은 정렬 대상 커밋 수입니다. 병합 정렬만 구현했으며 이 표는 성능 측정 결과가 아니라 알고리즘의 이론 비교입니다.

### 3-8. 시간·공간복잡도

V는 저장소 커밋 수, E는 부모 간선 수, B는 브랜치 수입니다. K는 검색 결과/후보 수, Q는 중복 제거한 검색 단어 수, P는 그 단어들의 인덱스 목록 길이 합, M은 가장 짧은 목록 길이입니다. L은 메시지 길이, U는 그 메시지의 고유 단어 수입니다. 아래는 딕셔너리·집합의 평균 O(1) 조회와 짧은 hash·키 비교를 가정합니다.

| 작업 | 시간 | 추가 공간·전제 |
| --- | --- | --- |
| 커밋 hash 조회 | 평균 O(1), 충돌이 심하면 최악 O(V) | 참조 반환 O(1) |
| 브랜치 생성·전환 | 평균 O(1) | 새 브랜치는 평균 O(1) 공간 |
| COMMIT·인덱싱 | 평균 O(L + U) | 토큰 임시 O(L), 새 인덱스 항목 O(U). 부모 최대 1 |
| LOG 기본 | O(V + E) | 남은 부모 수·큐·결과 O(V) |
| LOG 정렬 | O(V log V) | 병합 배열·슬라이스의 최대 동시 추가 공간 O(V), 재귀 스택 O(log V) |
| ANCESTORS | 방문 조상과 간선 수 O(Va + Ea) | visited·결과 O(Va), 중복 대기 항목을 포함한 스택 최악 O(Va + Ea) |
| PATH | 탐색한 연결 요소에 대해 O(Vc + Ec) | 거리·큐·결과 O(Vc). 경로를 고를 때 각 경로 노드의 이웃도 확인 |
| 한 단어 SEARCH | 평균 O(단어 길이 + K) | 현재 구현은 후보를 set으로도 복사하므로 O(K) |
| 여러 단어 SEARCH | 평균 O(검색 문자열 길이 + P + Q×M) | 후보 집합·결과 O(P + Q) |
| 작성자 SEARCH | 평균 O(이름 길이 + K) | 결과 복사·커밋 목록 O(K) |

조회 과정의 딕셔너리·집합 충돌 최악 상황에서는 위 평균 기반 식보다 느려질 수 있습니다. 문자열 비교 비용까지 계산하려면 키 길이를 함께 고려해야 합니다. 화면 출력 시간도 출력 문자 수만큼 필요합니다. 정렬 비교 횟수와 전체 문자 처리 비용은 구분하세요.

저장소는 커밋·간선·브랜치·역색인 항목·메시지 문자열을 보관합니다. 키워드 하나가 모든 메시지에 들어가면 결과 자체가 V개이므로 역색인이 있어도 출력까지 O(1)이 될 수 없습니다.

### 힌트·해설

## 5. 나중에 공부할 확장 지식

- 두 부모를 갖는 merge와 공통 조상: 현재 parents 모델을 확장해 활용할 수 있습니다.
- 파일 스냅샷·내용 기반 해시·압축 객체: 실제 Git의 데이터 저장으로 연결됩니다.
- 인덱스 변경·삭제: 지금은 커밋 생성만 있으므로 삭제 시 인덱스 정리 로직은 필요하지 않습니다.
- 영속 저장·원자적 쓰기·복구: 프로그램 재시작 후 기록을 유지하려면 필요합니다.
- 토큰화·구두점 처리·한국어 형태소: 현재 공백 단위 검색의 범위를 넓히는 주제입니다.

필수 미션을 이해한 뒤 별도 복사본에서 실험하세요. 현재 결과물이 실제 Git의 저장소 호환성이나 파일 복원 기능을 제공하는 것은 아닙니다.
